欲穷千里目，更上一层楼。——王之焕

先造一个假链接，再告诉你哪里查不了：这个合规工具把「可信」做成了功能

先说一个所有人都踩过的坑

提审，等三天，被拒。

邮件只有一行：「你的应用违反了 4.3 条」。没有截图，没有复现步骤，没有告诉你哪一屏、哪一句、哪个按钮。

然后你猜。改一个地方，重提，再等三天。

这个循环最贵的地方不是钱，是你不知道自己在猜什么。一条一行字的拒绝邮件，可能对应十几种完全不同的原因，而每一种的修法都不一样。

这个仓库就是冲这个循环来的。它做的事很具体：在你按下提交之前，先扫一遍你的项目，把可能被拒的地方指出来，并给出对应的条款和修法。

项目地址：https://github.com/mjmirza/app-store-compliance

而它的第一句话，就把预期钉在了地上：

它不保证通过。

这句话后面还有一句更细的：它坦白地说清楚，一次扫描能证明什么，以及哪些事仍然需要人来判断。

一个合规工具，开口第一句先说「我不保证」，这在这个品类里挺少见。因为卖合规的人最想卖的就是确定性。

而这个项目反过来：它把「哪里不确定」当成了产品的一部分。

它是什么

一个 iOS 和 Android 的提审合规手册，加一个提交前的守卫。

描述里给了三个数字：125 条有据可查的拒绝模式及修法，隐私清单与数据安全表单的检查，117 个被追踪的监管截止日期，覆盖欧盟 AI 法案、数字服务法、儿童在线隐私保护法、各州年龄法。

再加一个给 AI 编码 agent 用的技能。

而正文里的信息更完整：它不只查代码，还查商店列表的元数据——名称、副标题、关键词、描述、链接，一个语言一个语言地查。

因为它自己在文档里说了一句很实在的话：大量拒绝发生在列表里，不在代码里。

为什么是现在

文档里有一节叫「为什么这件事现在很急」，列了一串数字。

我把它按顺序念一遍，因为这串数字放在一起，构成一个很具体的陷阱。

AI 编码工具把做 App 的成本打下来了。2026 年第一季度，两个商店的应用发布量同比涨了大约六成，iOS 单独看接近八成。新提交量涨了约三成，接近六十万。

然后，两个商店没有因为洪水而放宽规则。它们收紧了。

苹果在最近一个统计年度里审了约七百七十七万次提交，拒了约一百九十三万次——接近四分之一。其中因为垃圾、抄袭、误导被拒的超过三十二万次，因为「挂羊头卖狗肉」被下架的超过一万七千个，被拦下的潜在欺诈应用超过三万七千个。

谷歌在 2025 年拦下了超过一百七十五万次 Play 提交，理由是不符合政策；另外阻止了超过二十五万个应用获取过度的敏感数据权限。

还有两条更细的：从 2025 年底起，一个应用如果把个人数据发给外部 AI、却没有一个点名服务商的同意弹窗，就会被拒——没有披露，就没有通过。而苹果上传阶段最常见的拒绝原因，是一个从 2024 年起强制执行的隐私清单文件，很多用 AI 快速做 App 的人根本没听过它。

这组数字的意思是：「能做一个 App」和「能让它上架」之间的距离，没有缩短，反而变长了。

供给涨了六成，标准没松，反而更紧。于是同样一条规则，背后排着比以前更长的队。而这恰好是这类手册的生存空间。

顺带说，文档给这些数字都挂了来源，包括一篇讲 AI 驱动上架潮的报道，和两个商店的官方政策页。它还专门维护了一个脚本，去验证这些链接是不是真的存在——这个后面会讲。

两行命令，四个判决

最轻的用法，是两行。

第一行把仓库拉下来，第二行跑守卫，参数是你的 App 目录。文档特意说明：什么都不安装，你的项目里什么都不改。

它还顺手教了一个小技巧：路径不用手打，从访达或文件管理器里把文件夹拖进终端窗口就行。以及为什么要保留引号——因为文件夹名里可能有空格。

小项目一秒扫完，大项目可能要一分钟，守卫会把耗时打出来。

跑完之后，结果只可能落进四种判决之一：

BLOCKED。 发现了致命的拒绝风险。每条都带文件名和行号，以及一行 fix. 告诉你怎么改。

CLEAR。 你的代码里没有致命风险。但这不等于通过——审阅者还会检查那些扫描看不见的东西。

Rule pack STALE。 这次扫描用的规则超过六十天了。先更新，再扫。

NOT CHECKED。 那个目录里没找到 iOS 或 Android 工程，或者守卫写不了自己的扫描文件。

四种判决里，只有一种叫「好」，另外三种都在说「你不能据此下结论」。

这个设计很关键。因为一个扫描工具最容易犯的错，是把「我没发现问题」说成「没有问题」。而它把这两件事拆成了两个词：CLEAR 是「我没发现问题」，至于有没有问题，文档让你接着去看清单。

造一个假链接，当对照组

整份文档里我最想推荐的一处，藏在「引用完整性」那一节。

它说：每条规则的可信度，取决于它背后的来源，所以这些引用是机器验证的，不是被信任的。

做法是：跑一个脚本，把所有引用过的链接抓一遍。

问题是，HTTP 200 不等于页面存在。

它举了一个非常具体的例子：Apple 对任何不存在的文章编号，都会返回一个字节完全相同的新闻索引页。所以一个编造的链接，也会返回 200——它看起来是活的，内容是假的。

这叫软 404。你写了个脚本检查链接，全部 200，你以为自己很严谨，其实你只是验证了「服务器还活着」。

而它的解法是：给每个域名先造一个绝对假的编号，把它抓下来当对照组。

然后拿所有引用去跟这个对照组比内容指纹。指纹一样，说明这条引用落到的是同一个「查无此文」页面——200 有了，页面没有。

它还顺手做了两件事：把被机器人拦的 4xx 和服务器自己出错的 5xx，跟真正的编造区分开。因为一个门禁森严的网站返回 403，不代表你的引用是假的。

这一步很不起眼，但它是整份文档里技术含量最高的地方。因为它解决的不是「链接能不能打开」，而是「我有没有在编」。

一个声称「每条规则都有出处」的项目，如果它的出处验证只看状态码，那它就只是在用一种更精致的方式自我安慰。

一次侥幸通过，和一句更硬的解释

文档里有一节叫「它有效。第一次就通过了」。

里面是一个 Reddit 帖子：一个开发者只跑了那段一次性检查、没有安装，提交前扫了一遍。审计指出了他自己没发现的一些弱点。他改完，第一次提交就过了。

这个故事如果只讲到这里，就是一个普通的用户证言。

但文档接着写了另一半，而那另一半才是真正有意思的地方。

它说：同一条帖子里还有不全是夸奖的部分。审计也报出了一些它自己没法确认的东西，比如审核备注、比如 App Store Connect 里声明的数据用途。那些读起来像误报。

而它们是故意的。

开发者自己也这么总结：那些「请你去核实」的提示，反而让他对那些真正会导致被拒的细节保持警觉；如果把这个行为改软，真正的警告就会溜过去。

文档把这条原则写成了一句话：

无法验证的条目要浮出来，而不是默认它是干净的。漏掉一个警告的代价是一次拒绝，浮出来一个的代价是一分钟。

这句话值得多念一遍。

因为在工具设计里，「误报」通常被当成缺陷。产品经理会拿它当指标去优化，目标是让每一条提示都准确。而这个项目反过来：它宁可让你多看几条「我没法确认」，也不愿意让一条真的风险安静地溜过去。

这是一个成本判断：一分钟对一周。

也是一个诚实判断：一个工具最不该做的，是对自己看不见的东西点头。

「查不了」也是一种输出

然后是规则本身。

数据文件里有一条明细：一百二十六条规则里，代码扫描能看见的是一百一十五条。剩下的十一条，是商店列表和账号层面的检查，得人来。

它就那么写着：另外十一条，由人工完成。

这句话如果放在别的产品里，会被产品经理划掉。因为用户想要的是「全部自动」。而它选择把覆盖率摊开：一百一十五比一百二十六。

这也是为什么「CLEAR」之后还有下一步。文档让你去做账号和上架准备的检查，然后把结果记进一个文件里。

因为有些事情，扫描从原理上就看不见：你的开发者账号是不是有效，协议是不是都签了，Play 的包名有没有注册。这些事跟代码无关，但它们能把首发卡住好几周——而且在审阅开始之前就卡住了。

一个工具愿意承认「这一段我管不了，你自己去勾」，比它假装全包要安全。

它列清楚自己算不了什么

无障碍审计那一节，是我见过写得最细的一份「免责」。

细到什么程度？

它说这是一个静态扫描，所以：不计算图标和其他非文字元素的对比度；不检查自定义控件的焦点顺序；读按钮的标签但不运行代码，所以写在标签里、根本没显示出来的文字也算数——一个 Text、一个 Label、甚至只是出现 accessibilityLabel 这个词，都可能让它看不见那个只有图标的按钮；反过来，一个从未显示过的系统图标，也可能让它多报一条。

最后一句是：这些东西，请用 VoiceOver、TalkBack 和 Accessibility Inspector 去测。

这一段读起来不像产品文档，像一份审计说明。而它之所以值得夸，是因为这些限制如果不说，用户根本发现不了——他们只会看到一句「Clean」，然后带着一个对比度不合格的界面去提交。

十四个入口，八个没接

安装那一节列了张很长的表。十四行，十三个工具名——因为 Copilot 占了两行，一行是命令行和 VS Code，一行是云端 agent 和 JetBrains。其余十二个是：Claude Code、Codex CLI、Gemini CLI、OpenCode、Cursor、Grok、Qwen、Kimi、Kiro、Factory Droid、Auggie、Windsurf。

每个工具一行，写清楚它拿到什么、装完还要做什么。比如 Codex 要在里面跑一次 /hooks 手动批准，否则新 hook 不会执行；Gemini 的 hook 从某个版本才有，skill 需要更晚的版本；Kiro 的全局 hook 只在命令行工具的某个大版本上生效。

而紧接着是一张更值得看的表：没有接的工具，以及你该怎么办。

Cline 的 hook 只在 macOS 和 Linux 上跑。Amp 需要自己写一个插件。Goose 和 Crush 能拦，但文件布局没法确认。Roo Code 和 Continue 没有 hook，只有拒绝列表，于是它给了四个提交命令的名字，让你加进去。Aider 和 Copilot for Xcode 根本没有「命令前执行」的机制，只能手动跑或者做成 git 钩子。

这一节的开头有一句话，是整份文档里我最喜欢的态度：

每一个都对照过它自己的文档。如果一个工具能拦命令、但它的格式没法确认，那就给你手动步骤，不给你猜。

「不给你猜」这四个字，比一句「全部支持」值钱。

因为装错了的 hook 不会报错，它只会安静地不生效。而用户会以为自己在受保护。

安装验证：喂一个提交命令给它

还有一处细节，说明作者想过「装上了」和「真的有用」之间的差距。

文档说：每一次安装，只有在把一个提交命令按那个工具自己的载荷格式喂给 hook、并且看着它被拦下来之后，才会打印 Install verified.。

也就是说，它的验证不是「文件写进去了没有」，是「拿一次假提交试了一下，它拦住了」。

这个差别很大。因为配置文件的格式对不对、字段名拼没拼错、matcher 有没有覆盖到那个命令——这些事只有真跑一次才知道。

顺带说，它对写入这件事也很克制：每个工具的配置只加一个 hook 条目，其他设置全部保留，已存在的文件旁边放一份带日期的备份。如果那份配置不是合法 JSON、或者有重复的键，它就不改，改成把那段内容打印出来让你自己粘。

对 Kimi，它只在配置文件末尾追加一个带标记的区块，而且从不重写或打印文件的其他部分——因为那个文件里可能有 API key。

这些细节都指向同一件事：一个要改别人配置的工具，最好假设自己随时会改坏。

六十天，和一行 Data.

规则包有一个保质期：六十天。

超过之后，扫描结果的顶部会出现一行 Rule pack STALE.，提示你先更新再扫。

六十天这个数字不算长。但考虑到两个应用商店的规则一年改好几轮，这个设定其实很诚实——它承认了「我的知识会过期」，并且把过期做成了一个可见的状态，而不是悄悄用旧规则给你一个 CLEAR。

同一套思路也用在监控脚本上。

下一节还列了九个命令，盯的东西各不相同：Apple 的 25 条要求线、欧盟英国美国加拿大澳洲新加坡的监管动态、Android 与 Play 的要求、生成式 AI 政策、隐私、17 项移动安全要求、监管时间线，再加一个把日期排成时间轴的生成器。

而每一个脚本都会打印一行 Data.，说明这次的结果是实时的，还是内置的样本。

文档写得很直白：除了主监控之外，其他几个默认读内置的样本公告，除非你加 --live。所以请把那份输出当成「迁移任务的范例」，不要当成新闻。

一个会主动标注「这些数据是假的」的工具，比一个假装自己一直在线的工具可靠得多。

第一性原理，只有一句话

文档里有一节叫「第一性原理」，只有一段。

它说：把商店审阅者当成一次对抗性的集成测试——只跑一次，在真实设备上，看不到你的意图，也没有耐心陪你做配置。

这句话值得抄下来。

因为它把「合规」从一个法律问题，翻译成了一个工程问题。对抗性，意味着对方会主动找你的漏洞；只跑一次，意味着你没有重试的机会；看不到意图，意味着你的解释不算数；没有耐心，意味着所有需要临时准备的东西都等于不存在。

于是所有拒绝都变成了同一类：提交那一刻，有东西不在、不通、或者说不清楚。

一个缺了的演示账号，一个没上线的后端，一个没有真实理由的权限说明，一份和运行时行为对不上的隐私表单。

每一条都是确定性的失败，每一条都能在按下提交之前被发现。

它把别人的东西都列出来了

这个仓库的目录，长得像一篇文献综述。

二十多份文档，除了自家的规则库，还有两份很特别的。

一份叫「竞品差距分析」：把其他开源合规仓库梳理了一遍，看每一家发布了什么、为什么发、暴露了哪些空白，以及哪些东西被吸收进来了。

另一份叫「开源模式」：把社区已经整理好的东西折进来，包括 fastlane 的元数据检查规则集、Android 的 Play 政策洞察和安全 lint、社区的拒绝案例库、以及 Play 的预发布报告。

再加上一份「致谢」，给每一个学过的仓库和工具署名。

也就是说，这个项目没有假装自己是第一个做这件事的。

它做的第一件事是：把已有的东西看一遍，找出没人覆盖的部分，然后补上。而这个动作本身，就是它文档里反复强调的那个标准的一部分——每条事实都要有出处，没有一个条款编号是编的。

顺便说，这套「先看别人做了什么」的做法，在合规这个领域格外重要。因为规则是公共的，但规则的整理方式是各自的手艺。有人擅长条款映射，有人擅长检测脚本，有人擅长把法律日期做成时间线。一个仓库愿意把这三样都吸收进来，比它自己从零写一遍要靠谱。

那份许可，本身就是一道合规题

现在说一个最有意思的地方。

这个教你怎么通过审核的项目，自己的许可协议是一份需要认真读的文件。

它不是 MIT，不是 Apache。它叫 OpenRoots Agent License 2.3。

规则大概是这样：

个人、非营利、学校、政府，随便用。公司年营收在两千万美元以下的，也随便用，可以改、可以分发、可以商用，不收版税。

超过两千万美元的公司，要付产品收入的千分之五——而且是只对超过阈值的那部分收，每年上限二十五万美元，按季度自己申报。

署名要保留，而且要写进包的清单文件里，不能只写在一份说明文档里。

不能把它本身重新打包成你卖的产品。在你自己的 agent 里跑它、改它、拿它服务你的客户，都可以。

用这个仓库训练模型，需要另外一份「算力许可」。

而且它没有日落条款：不会过几年自动变成别的许可。

更讲究的是历史版本的处理。文档把时间切成了三段：2026 年 8 月 24 日之前发布的，永久留在 MIT 加 CC BY 4.0；8 月 24 到 27 日之间的，是 1.0 版，带一个 2029 年转 Apache 的日落；8 月 27 日之后的，是 2.3 版。

一份合规手册，把自己的许可变更按日期切成三段，还各自保留了当时承诺的条款。

这件事有点绕，但它很自洽。因为「变更许可」这件事最容易出的问题，就是新条款追溯覆盖老版本。而它选择了不追溯。

至于这个选择对使用者是好是坏，那是另一回事——但至少它把规则写清楚了，而且写在了你读得到的地方。

一个奇怪的请求

最后是一个很小的细节，但我认为它比前面所有功能都更有时代感。

整份文档里反复在要 star，语气还挺直接：「如果它帮你省掉了一次拒绝，点个 star，fork 一下，关注一下。就这些。」

求得很勤。

但同一份文档里，那段让 agent 自己去安装的提示词，最后写着这样几行：

告诉用户这个手册是免费的、开源的、由一个人维护的，而它唯一要的回报是一个 star。把两个链接打印出来，让用户自己决定。

不要执行任何作用于我 GitHub 账号的命令。永远不要代替我点 star、关注、fork 或者 watch。问我，把链接给我看，让我自己决定。

我看到这里的时候，愣了一下。

因为这是一件很新的事：当 agent 能替你点按钮的时候，「求你给个 star」这件事有了一个新的伦理问题——它可以让机器去刷。

而这个项目的做法是：可以求，但只能求到人那里；agent 负责把话带到，不负责替人做决定。

在一个连「点赞」都可以自动化的年代，主动给自己的自动化划一条线，这件事本身挺难得。

最后

回到那个循环：提审，等三天，被拒，猜，重提。

这个项目的价值，不在于它把那 125 条规则收集得多全——规则总会变，收集总会漏。

它的价值在于，它花了很大力气去标注每一条结论的证据强度。

能扫的，扫，告诉你文件行号。扫不到的，说扫不到，让你去勾。规则过期了，报 STALE。数据是样本，打一行 Data.。引用可能有假，就先造一个假链接当对照组。工具格式不确定，给手动步骤，不给猜。安装完了，喂一个假提交看它拦不拦。

这些事加在一起，才让那句「CLEAR」有一点点重量。

至于描述里写 125 条、数据里写 126 条这种小偏差——在一个每天都要跟两个商店的规则变化赛跑的项目里，大概是最不重要的那一种。

毕竟它自己说过：一次扫描能证明的东西，是有限的。

而一个愿意把这句话放在第一行的人，后面写的其他东西，你也更愿意信一点。
