天下兴亡，匹夫有责。——顾炎武

CI 红了之后，你按下的那次重跑，其实什么都没查

一个所有人都在做、但几乎没人承认的动作

流水线红了。

第一反应通常不是打开日志，而是去找那个环形箭头。点一下，刷一会儿手机，绿了。于是今天继续。

这个动作本身没有错。问题在于它不产生任何知识。它解决了一次红灯，却没有说清这次红灯属于哪一类：某个测试本来就时灵时不灵，构建机的磁盘快满了，上游依赖刚发了个坏版本，或者你真的写错了。

下一次红灯来的时候，你还是只能再点一次。

这件事在团队尺度上会积成一种很奇怪的状态：所有人都知道流水线不可靠，所有人都学会了重跑，但没人能说出不可靠的那部分到底占多少。因为重跑这个动作，恰好把证据销毁了。

OpenSRE 就是冲这一步来的。

项目地址：https://github.com/Tracer-Cloud/opensre

它的描述只有一句：面向 CI/CD 可靠性的开源 agent。副标题写得更具体：一个 CLI agent，读失败的运行、追出原因、推一个补丁给你 review，自托管，用你自己的模型。

那句开场白，比任何功能列表都准

文档里有一句话，是整份材料的钥匙：

AI 每个月写掉越来越多的代码。但修构建这件事，还是得有人干。

这句话没有攻击任何人，它只是把一种结构性的错位摆了出来。写代码的成本在下降，所以代码变多了；而流水线红了的次数，大致和代码量成正比。于是「修构建」这件纯人力的活，工作量在涨，而愿意干、干得好的人，永远是那几个。

接下来那段诊断更狠。它说流水线红了之后，只会告诉你有事发生了，不会告诉你为什么，也不会告诉你怎么修。而在交付期限的压力下，团队按下重跑，继续往前走；不稳定的检查越积越多，主分支一直红着；真正的调查，被推给「哪个资深工程师有空」。

这段话里的每一个动词都是真实发生过的。重跑、继续、积压、红着、等。

然后它给了四条承诺，四条都在回应这段诊断：

更快地从红构建里恢复。 运行一失败它就开始查，读日志、试假设，最后推一个补丁给你 review。

修原因，不只是重跑。 它把「CI 自身导致的失败」和「代码导致的失败」分开，好让你修对的那个东西。

知道 CI 在花你多少钱。 失败率、因不可靠 CI 损失的开发者小时、以及主分支红了多久。

每个人都能拿到资深级别的上下文。 同一个团队里，每个人得到的分析深度是一样的。

四条里，第二条是骨架——另外三条都靠它撑着。所以它值得单独拆开讲。

那条最值钱的分界线：是 CI 坏了，还是代码坏了

这是我读完这份文档后认为最重要的一件事。

一次红灯背后，其实是两个完全不同的世界。

一个世界里，坏事发生在流水线自己身上：某个 runner 的资源不够，某个测试依赖了执行的顺序，某个第三方服务在那一刻超时，某个缓存的 key 刚好撞上。这类失败，重跑一次确实会好。而且它下次还会坏，坏在别的地方。

另一个世界里，坏事发生在你的改动里：类型对不上、断言写错了、迁移脚本没跑、某个边界条件没考虑。这类失败，重跑一百次也还是红的。

而重跑这个动作，恰好对两个世界给出同一个反馈。绿了，你以为是前者；红了，你才承认是后者。中间那段信息，全丢了。

于是团队会形成一种很糟糕的能力退化：遇到红的先重跑，重跑不好再看日志，看日志看不懂就加个 retry。一年之后，流水线里躺着一叠重试，而没有人知道哪一层在掩盖真问题。

OpenSRE 做的事，是把这个分类动作从人手里接过去。它去读失败的检查、读 CI 日志、读最近的提交和部署、读相关联的日志指标和链路，然后在这些东西之间做假设检验，最后给出一个判断：这次是 CI 的锅，还是代码的锅。

这个判断听起来平淡，但它决定了你接下来八个小时干什么。修 CI 是运维动作，修代码是开发动作，两者的负责人、时间成本、复盘方式完全不同。分错了，你就把八个小时花在了错的那一半。

三个数字，第三个最扎人

「知道 CI 在花你多少钱」这条承诺下面，列了三个指标。

失败率——这个是常规的，任何 CI 面板都能给。

因不可靠 CI 损失的开发者小时——这个开始有意思了。它把「红灯」从一次事件转换成了一个人力单位。一次红灯的真正成本不是那几分钟的等待，是三个人各自打开日志、各自怀疑自己、各自点了一次重跑的那段时间。

主分支红了多久——这一个是三个里最扎人的。

因为它不是一个技术指标，是一个组织指标。主分支红着，意味着所有人的合并都被堵住，意味着有人开始在自己的分支上堆更多改动，意味着明天要处理的合并冲突更大。它是一个会自我放大的数字。

而这个数字，几乎没有人统计。大多数团队能说出「上周有几次失败」，说不出「上周主分支累计红了多少小时」。

一个把这三个数字并排放的工具，其实在改变一件事：它让「CI 可靠性」从一个只能抱怨的话题，变成了一个可以汇报的指标。

一次体检、一次救火、或者一个常驻的人

文档给了一条建议，说「从这里开始」，然后列了三件事：分析一个仓库的 CI 可靠性，修一个 PR 上失败的检查，或者起一个能一直让 CI 保持绿的 agent。

这三件事，其实是三种完全不同的姿态。

体检。 你还没出事，只是想知道自己有多不稳。跑一次，拿到失败率，拿到主分支累计红了多久。它的产出是一份诊断，不是一个修复。

这个姿态的价值被严重低估了。因为大部分团队对自家 CI 的印象，是由最近三次特别难受的红灯构成的——那是一种记忆，不是一个统计。而记忆和统计之间的差距，往往大得离谱：你以为最痛的是那个总在半夜挂掉的端到端测试，认真算一遍人时才发现在它身上花的时间，还不如每周五下午集体等构建的那两个小时。

救火。 一个 PR 红了，你不想花两小时去读日志。这时候它读一遍，给出判断，推一个补丁到分支上。

这一档有个前提条件，文档在「开始之前」就写了：你需要一个 git 仓库，因为完整的流程要往分支上推东西。它把这条写成「建议」，措辞很客气，但意思很清楚——没有仓库，你只能拿到分析，拿不到补丁。

值班。 第三种最不一样。前两种是你去调它，第三种是它一直在那儿。

一个「让 CI 保持绿」的 agent，不是一次调用，是一个岗位。它得接到告警、得自己判断、得在判断完了之后主动把结论推到某个地方去。这也解释了为什么这份文档里会同时出现 Slack、PagerDuty、Telegram、Discord 这些名字——它们不是集成清单里的装饰，它们是这个岗位的工位。

从工具到同事，中间隔的就是这一档。而这一档恰好也是最难做好的：一次性任务答错了，你重跑一遍；常驻岗位判断错了，它会安静地一直错下去。

六个动作，第二步是「遮住」

流程被拆成了六步，每一步都能对应到一句人话。

取。 拿失败的检查和 CI 日志，拿最近的提交和部署，拿相关联的日志、指标和链路。

遮。 在调用外部模型之前，把敏感的标识符盖掉。这一步是可选的。

推理。 在你接进来的那些系统之间做假设检验，走一个工具调用的循环，最后分开 CI 导致的失败和代码导致的失败。

答。 在对话里给一个有证据链接的回答。

修。 把原因修掉，推到 PR 分支上等你 review；或者给出下一步建议，并且在可选的情况下执行修复动作。

发。 把摘要直接贴到 Slack、PagerDuty 或 Telegram，不用切窗口。

六步里，最容易被略过的是第二步，而它恰好是最该被单独拿出来说的。

因为它承认了一个很硬的事实：查 CI 的时候，你要把一堆日志和指标交给一个模型。 那里面可能有内部主机名、可能有客户标识、可能有不该出门的路径。所以「遮」不是加在最后的一道合规工序，它是排在「推理」之前的前置条件。

顺序本身就是态度。先遮，再想。

而第五步里的「推到 PR 分支上等你 review」也值得停一下。它没有说「自动修复」，它说的是推到分支上、由你来看。这个措辞守住了那条线：合并的权力还在人手里。

三个入口：你可以住在里面，也可以只调用一次

很多 agent 工具默认一件事：你会住进它的界面里。

OpenSRE 给了三个入口，三个入口的粒度完全不同。

交互式 shell。 不带子命令直接跑，它会校验你的账号，然后起一个 REPL。你可以用平实的话描述一次事故，看它干活；也可以用斜杠命令控制会话：帮助、状态、花费、会话列表、恢复、压缩上下文、新建、退出。另有一组管集成的命令，用来列出和校验。

这些命令里有两个细节很说明问题。一个是 /cost——它把「这一轮查下来花了多少」做成了一条随手可查的命令，而不是藏在一个账单页面里。另一个是文档里那句：Ctrl+C 取消正在进行的一轮，但不会丢掉会话状态。

取消但不丢状态。这是所有长任务工具都该有、但很多都没做到的一件事。

而文档里那句「把它嵌进同事已经在用的 Python 服务和自动化里」，其实是在回答一个战略问题：这个工具想成为你打开的一个应用，还是想成为你系统里的一个部件。它的答案是后者。

上面那段 Python 代码里，藏着一个很容易被读漏的细节。

代码里有一段注释，大意是：answered 为真，只代表有回复文本，包括一次失败的模型调用。而那种情况下，accounting_status 会是 not_run，stop_reason 会是 error。

这句话值得念两遍。

因为它把一个几乎所有 AI 工具都在含糊处理的问题，明确拆成了两个字段：有没有输出，和这一轮到底跑成了没有。

一个失败的模型调用，也可以产出一段文字——一句「抱歉，我无法完成」、一段被截断的推理、一个空的回答包装。如果你只判断「有没有文本」，你就会把失败当成功，然后把一个错误的结论当成证据往下传。

而这个 API 的选择是：文本归文本，记账归记账。想知道这一轮成不成，去看 accounting_status；想知道为什么不成，去看 stop_reason。

在一份产品文档里，这种字段级别的诚实比十句「可靠」「可信」都值钱。因为它意味着写这段代码的人，真的被「看起来成功了」坑过。

60 多个集成，和一个带限定的 Trello

集成表按类别铺开，一共十类，横着读会发现它覆盖的不是「CI 工具」，而是「一次事故能牵扯到的所有地方」。

模型。 Anthropic、OpenAI、OpenAI Codex、Ollama、Google Gemini、OpenRouter、TrustedRouter、NVIDIA NIM、Bedrock。

可观测性。 Grafana 的四件套，Loki、Mimir、Tempo 和注解；Datadog、Honeycomb、Coralogix、groundcover、CloudWatch、Sentry、Elasticsearch、Better Stack、Splunk、Victoria Logs、SignOz、OpenObserve、OpenSearch、Azure Monitor、New Relic。

基础设施。 Kubernetes、AWS 的六项、Azure、ArgoCD、Helm。

数据库。 MongoDB、ClickHouse、PostgreSQL、MySQL、MariaDB、MongoDB Atlas、Azure SQL、Snowflake、Redis、RDS、Supabase、Neon。

数据平台。 Airflow、Kafka、Prefect、RabbitMQ、Dagster、Temporal。

开发工具。 GitHub、GitHub MCP、Bitbucket、GitLab、Jenkins。

事故管理。 PagerDuty、Jira、Alertmanager、incident.io、ServiceNow、Trello。

沟通。 Slack、Google Docs、Discord、Telegram、Rocket.Chat、WhatsApp、Buzz。

部署。 Vercel、EC2、ECS、Railway。

协议。 MCP。

十类里，最值得看的不是数量，是那个唯一带限定的条目：Trello 后面跟着一句「仅客户端辅助」。

六十多个集成，只有一个被主动打了折。而这个折打得挺勇敢——它本可以什么都不说，把 Trello 和 PagerDuty 并排放着，让你自己去发现它只能干一部分活。

还有一列是 Roadmap：Linear 挂着一个 issue 号，Notion、Teams、Confluence 各挂一个。四个还没做的东西，四个可以点进去看的工单。

一个集成表愿意把「做了什么」「做到什么程度」「还没做什么」分成三栏，这张表就已经不只是功能清单了，它是一份进度声明。

部署三条路，中间那条很奇怪

部署选项给了三条，三条的气质完全不同。

托管网关。 组织管理员在 web 应用里开通，之后已登录的 shell 用户可以直接查状态、启动、停止，本地不碰任何基础设施凭证。

这一条解决的是一个很具体的组织问题：谁有权开这台机器，和谁能用它，往往不是同一个人。

网关，AMI 加 systemd。 先构建镜像，再部署。文档特意标了一句：只做 Telegram 网关，不用 Docker；网关被装进一个服务器镜像里，新服务器从这个镜像启动。

这条是三条里最反常的。

一个满世界都在谈容器编排的项目，部署路径里居然有一条是「把服务烤进机器镜像」。这不是落后，这是另一种世界观：如果这台机器是一次性的，那就该装进镜像里，而不是装进容器里再拉起来。机器坏了就换一台，换的那台从同一个镜像起来，状态不在机器上。

自托管容器。 部署仓库里的 Dockerfile，选一个模式，设好模型提供方和它的 key。只有当网关需要共享的 Postgres 状态时，才用数据库连接串，比如 Slack 事件 API 的多副本。

三条路的差别不在难易，在「谁负责这台机器活着」。第一条是厂商，第二条是你的镜像流水线，第三条是你的编排系统。

而这三条能同时存在，说明它没打算规定你必须怎么运维。

一个把卸载写进文档的 CLI

快速开始那一节末尾，列了三条「其他有用的命令」：

第三条，注释写着：移除 opensre 和所有本地数据。

这个细节小到几乎不占篇幅，但它很少见。

大多数 CLI 工具不写卸载。原因不难猜：写卸载等于承认用户会走；而写「连本地数据一起删」，等于承认这个工具在用户的机器上留下了东西。

而它把这件事写在快速开始里，不是写在某个 FAQ 的第三屏。等于在你装之前就告诉你：想走的时候，一条命令能走干净。

一个敢把出口标在入口旁边的工具，通常对自己的留存没那么焦虑。

它把自己的成熟度标成了「公开 alpha」

文档顶上挂着一排徽章，其中一个写着 status: public alpha，橙色的。

正文里对应着一句提示：核心工作流可以用于早期探索，但还没有完全稳定；项目在活跃开发中，API 和集成可能变化。

这句话和那六步流程放在一起，会形成一种挺好的张力：一边是一套看起来相当完整的架构，一边是一句「还没稳」。

很多项目会把这句话删掉，或者挪到文档最底部。这一份把它放在第一屏。

还有一件事得说清楚，因为它容易被「自托管」这三个字带过去。

副标题写的是「自托管，用你自己的模型」，但快速开始里的第一句是：第一次启动会激活托管模型。

两句话不矛盾，但需要一起读：默认路径是托管模型，自己的模型是你后来选的。集成表里那一列九个模型提供方，包括 Ollama，就是那个「后来」。

这不是什么问题。启动成本低一点，报名率高一点，是合理的产品选择。只是读文档的时候，别把「支持」读成「默认」。

遥测那一节只有两段。

第一段说，第一方的产品分析和 Sentry 错误上报都是 opt-out，也就是默认开着。

第二段给了一条命令：

就这么简单。一个变量，设了就是关。

我欣赏这种写法的地方在于它没有绕。它没说「我们非常重视您的隐私」，也没给一个藏在三层设置里的开关。它说的是：默认开，一个变量关，完整的清单在另一个文档里。

而安全那一节，把边界划得更细：结构化的、可审计的模型提示词；默认本地处理对话记录；不做原始日志的静默批量导出。

「静默批量导出」这个词组选得很准。它没有承诺「我们不导出日志」——因为查事故本来就需要把日志给模型看。它承诺的是：不做你没被告知的那种批量外传。

一句能被追问的承诺，比一句漂亮的承诺有用。

拿 SWE-bench 论证自己该怎么被测试

这一段是我在这份文档里最想推荐的部分，因为它不像宣传，像一份方法论。

它先说：SWE-bench 表明，agent 在有真实任务和清晰反馈的条件下进步最快。

然后它做了一个类比：流水线的失败，比本地的代码任务更慢、更吵、更难复现。所以我们用同样的标准要求自己，具体做法有两条。

第一条，在云端支撑的场景里跑真实的端到端测试。

第二条，坚持语义化的测试目录命名，让「端到端与单元」「本地与云端」这两条边界一直清楚。

第二条听起来像代码规范，其实是个很硬的决定。因为测试目录的命名，决定了半年后一个新贡献者能不能在三十秒内找到「我该把这条测试加在哪」。而这件事一旦含糊，测试就会慢慢长成一锅粥，最后没人敢删任何一条。

把「我们怎么被测试」写成一段有引用的推理，而不是一句「我们有完善测试」，这是很少见的自觉。

顺便说一句，那段引用指向的是一篇论文。一份产品文档为了解释自己的测试策略去引一篇论文，这个动作本身就在说：这个团队把「可靠性」当成一个要论证的命题，不是一个要宣称的品质。

还有一句藏得很深的话

「工作原理」那一节末尾，有一句几乎会被跳过的说明：当前代码级的 agent 架构，是在移除旧的图与链框架层之后的样子，见仓库里的那份说明文件。

移除旧的图与链框架层。

这句话背后是一整段工程史：很多 agent 项目一开始都是用一个编排框架搭起来的，节点、边、状态图、链。搭得快，但调试的时候你得同时理解两套东西——你的业务逻辑，和框架对你的想象。

而这个项目选择了把它拆掉。

拆掉之后得到的是什么？文档没细说，只把细节指向了另一份文件。但可以确定的是，拆掉一层抽象之后，一次工具调用从哪来往哪去，变得可以直接读代码看出来了。

对一个要跑在生产事故里的工具来说，可调试性不是加分项，是入场券。

最后

回到那个环形箭头。

它不是个坏按钮。它只是不回答任何问题。

而一个团队要往前走，缺的从来不是更快的重跑，是有人能在你按下它之前说一句：这次重跑有用，因为坏的是 runner；或者这次别重跑，因为坏的是你昨天那个迁移脚本。

OpenSRE 想做的，就是把这句话说出来。它得先读日志、先遮住敏感信息、先在几个系统之间试假设、最后才敢下判断；判断完了，它把补丁推到分支上，让你 review，把摘要贴到你本来就在看的那个聊天窗口里。

这条链子上没有一步是魔法。难的是把每一步都做得可以被追问。

至于它自己承认还在公开 alpha，承认有一个集成只支持一部分，承认有四个东西还在路线图上——这些坦白加在一起，反而让那六步流程显得可信了一点。

一个工具愿意告诉你它现在几岁，通常说明它打算活到长大。
