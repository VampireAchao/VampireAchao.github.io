又一个 agent 协议：AG-UI 想替「agent 和界面」这段路定规矩

先说个不太客气的事实

这两年，agent 相关的协议比 agent 本身还多。

给 agent 工具的，给 agent 之间说话的，给 agent 记记忆的，给 agent 找同伴的——每个都自称「开放标准」，每个都希望你第一个接。

结果开发者的处境变成了：你在选一个技术栈，顺便选了一个阵营。

AG-UI 就是在这个背景下出现的，而且它的位置选得挺聪明：它不抢工具，也不抢 agent 之间的通信——它抢的是最后一公里，agent 和用户界面之间那一段。

项目地址：https://github.com/ag-ui-protocol/ag-ui

它的描述只有一句：AG-UI，agent 与用户交互的协议，把 agent 带进前端应用。

它规定了什么

说得很朴素：在 agent 执行期间，后端发出与 AG-UI 约十六种标准事件类型兼容的事件；后端也能接受几种简单的、AG-UI 兼容的输入作为参数。

就这两句。

没有规定你必须用什么框架，没有规定事件必须是 JSON 还是二进制，没有规定你得跑在什么运行时上。它只规定了「说哪些话」和「听话的时候能听懂哪几句」。

然后是那个词：约十六种。

我很喜欢这个「约」。一个标准最关键的东西是事件类型表，而它连这个都不肯给你一个绝对数字。这不是草率，这是诚实——因为一个活着的协议，事件表一定会变；今天写死十六，明天加了两个，文档就成了谎言。

起步就一行

文档给的上手方式，短到不需要教程：

一行命令，一个骨架。

对一个协议来说，这个设计很关键。协议最容易死在「我知道它重要，但我不知道从哪开始」——规范读完了，代码还没写一行。而一行命令能跑起来的东西，才有机会被真正评估。

协议栈里的座位表

它把自己和另外两个协议并排放，用三句话说清了分工：

MCP 给 agent 工具。

A2A 让 agent 之间互相通信。

AG-UI 把 agent 带进用户面前的应用。

这三句话看完，你会意识到一个尴尬的事实：前两件事都有协议了，唯独「agent 怎么和人所在的那个界面说话」，一直靠各家自己想办法。

有的用 WebSocket 自己定义一套消息；有的把 SSE 包一层；有的干脆让前端轮询。于是每一个 agent 产品都要重写一遍「流式输出怎么传」「工具调用怎么显示」「用户打断怎么办」。

AG-UI 赌的就是这件重复劳动值得被标准化。

为什么是事件，不是状态

协议这个词容易被理解成「一份格式说明」，但真正的分歧在于：你同步的是消息，还是状态？

如果是状态，那协议要定义的是「一个界面此刻应该长什么样」。这更像 Redux 或 CRDT 那一套：大家对齐一份快照，谁改了谁通知。

AG-UI 选的是事件。

事件的意思是：agent 说「我开始回答了」「我调用了这个工具」「这个工具返回了这些」「我说完了」。至于界面怎么画，是客户端自己的事。

这个选择的代价是客户端要多做一点工作——它得自己维护状态、自己把事件流拼成一个界面。

但收益也明显：事件本身天然是一份流水账。一次执行发生过什么，按顺序摆在那里；而状态快照只告诉你最后的样子，中间怎么走到那一步，得靠猜。

对一个需要「可解释」的产品来说，过程比结果值钱。

中间件：宽进，但没说自己严出

技术那一节里，有两句关键的话。

任何事件传输都能用。 SSE、WebSocket、webhook，随你。

允许松散的事件格式匹配。 这样才能覆盖足够多的 agent 和应用。

第二句值得多想一秒。

「松散匹配」意味着它没打算当一个严格的校验器。这对生态是好事——现成的 agent 不用大改就能接进来；但对排错是坏事——当一条事件没被正确识别时，你很难判断是发送方不规范，还是接收方太宽容。

这是一种典型的协议取舍：先让人进来，再慢慢收紧。

而它同时给了两样东西来降低这个风险：一份参考的 HTTP 实现，和一个默认连接器。也就是说，你可以不用自己实现协议，先用它给的这套跑通，再考虑替换。

标准的推广从来不是靠规范文档，是靠「五分钟能跑起来」。

六件事，都是真实痛点

功能列表那六条，每一条都对应一个具体场景。

实时的 agentic 对话与流式输出。 这是最基础的：字要一个个出来，不能等整段生成完。

双向状态同步。 这条最难。agent 在后台改了状态，界面要跟着变；用户在界面上改了东西，agent 也要知道。单向的数据流在这里不够用。

生成式 UI 与结构化消息。 让 agent 不只是输出文字，而是输出一个界面片段。

实时上下文补充。 用户在界面上的动作——选了哪个下拉框、滚到哪、点了什么——都能作为上下文喂给 agent。

前端工具集成。 工具不一定要跑在后端。有些工具天然属于浏览器，比如操作当前页面。

人在环协作。 agent 停下来等你确认，这一步在很多产品里是靠「你自己看着办」糊过去的。

六条里有三条是关于「状态」的：同步、上下文、人在环。这不是巧合——agent 和普通聊天机器人最大的区别，就是它有状态、会动手、需要批准。

客户端也不止是网页

「把 agent 带进前端应用」这句话，容易让人以为它只关心浏览器。

看客户端那张表，会发现不是。

CopilotKit 是官方那一档。终端加 agent 是社区档——对，终端也算一种界面。Slack 和 Microsoft Teams 走的是 Channels SDK，被列在官方档。React Native 在官方档。OpenBot 也在官方档。

终端、聊天软件、移动端、机器人——四种完全不同的载体，共用同一套事件。

这才是「协议」和「组件库」的区别。组件库只能服务一种渲染环境；协议只关心「发生了什么」，不关心「画在哪」。

一个在 Slack 里跑 agent 的团队，和一个在 React Native 里跑 agent 的团队，从此可以共用同一套后端事件。这件事听起来平淡，但它省掉的是两套并行维护的推送逻辑。

集成表：三种身份，最真实的一节

支持列表很长，但它用三个标签把关系分得很清楚，这一点很值得学。

Partnership。 LangChain 和 CrewAI。文档还交代了来历：AG-UI 诞生于 CopilotKit 与这两家的早期合作。

1st Party。 微软 Agent Framework、Google ADK、Google Antigravity、AWS Strands、Mastra、Pydantic AI、Agno、LlamaIndex、AG2……以及还在进行中的 AWS Bedrock Agents。定义是：平台内置了 AG-UI，并且提供了文档。

Community。 Claude Agent SDK、Claude Managed Agents SDK、Langroid、Omnara、Cloudflare Agents，以及进行中的 OpenAI Agents SDK。

三种身份，三种承诺强度。

这套分法比「支持 30 个框架」这种笼统说法诚实得多。因为「支持」这个词在开源世界里被用得太松——有的是官方团队在维护，有的是某人写了个适配器然后不再更新，有的是「理论上能跑」。

而把它分成三栏，等于告诉读者：这一栏你可以放心依赖，那一栏你要自己看一眼。

顺便说，整张表里最尴尬的一处，是 C++ SDK 那个链接带着 c%2B%2B——因为加号在 URL 里得转义。一个想统一 agent 交互的协议，最后还是要向 URL 编码低头。

八种语言的 SDK，三种在路上的

SDK 那一栏，全部标着 Community：Kotlin、Golang、Dart、Java、Rust、Ruby、C++、.NET。

再加三个进行中的：Nim、Flowise、Langflow。

八种语言，没有一种是官方主力维护的——这件事不丢人，反而说明协议的抽象足够薄，薄到社区能自己写出来。

一个协议如果必须由核心团队提供每种语言的 SDK 才能用，那它大概率设计得太重了。

Dojo：每个例子 50 到 200 行

文档里有一节叫 Dojo，中文大概是「道场」。

它做的事很朴素：用一堆小而聚焦的例子，演示 AG-UI 的核心积木，每个例子只有 50 到 200 行代码。

这个数字很有说服力。

因为「示例代码」最常见的失败方式，是它本身就是一个完整应用：你要读三个配置文件、跑两个服务、配一个 key，才能看到「流式输出」这四个字长什么样。

而 50 到 200 行，意味着你可以把整个例子读完，然后说「哦，原来就是这么回事」。

标准组织的道场，比它的规范文档更能决定别人会不会用。

最后

回到开头那个选边的问题。

协议这件事，从来不是「谁更正确」，是「谁的表先被填满」。MCP 赢在它先让所有人接工具，A2A 在赌 agent 之间会需要对话，而 AG-UI 赌的是——下一个战场不在后端，在前端。

因为用户不关心你的 agent 用了什么框架、调了什么工具、跟哪个 agent 通了话。用户只看见一个界面：字有没有流出来、按钮点了有没有反应、它停下来问我的时候，我能不能看懂它在问什么。

这三件事没有标准，就只能每家自己写一遍。

AG-UI 现在做的事情，就是把这件重复劳动收归公有。它能不能成，不取决于规范写得多漂亮，取决于那张表上的「1st Party」那一栏，明年会不会变得更长。

至于那句「约十六种事件」——一个愿意在关键数字前加「约」的协议，至少比那些把自己写成宇宙真理的，更像个能干活的。
