一个 TypeScript 仓库，第一件事让你装 Rust：Firecrawl 把同一套 API 拆成了三种形态

先说一个反常的细节

打开这个仓库，语言那一栏写着 TypeScript。

然后文档的第一个安装命令是：

Rust。

一个以 TypeScript 为主的项目，把「在你自己的机器上跑」这件事，做成了一个 Rust 二进制。这个选择本身就值得停一下。

更反常的是它紧接着写的那句话：如果你没有 Rust，云端跑同样的抓取，不用构建，也不用注册。

一份文档，在你还没开始编译之前，就把退路指给你了。

这种写法有两种可能：要么是对产品没信心，要么是太清楚「装个编译工具链」对多少人来说是终点。

读完后面那几节，我倾向后者。

项目地址：https://github.com/firecrawl/firecrawl

它现在说自己是什么

描述只有一句：让你的 agent 更聪明的知识基础设施。搜索、抓取，并通过一个 API 访问 550 多个数据提供方。

「知识基础设施」这个词，比「网页抓取 API」大了一圈。而正文第一段就把这个「大」拆成了三条具体的路：

Firecrawl Local。 在你自己的机器上跑，一个二进制，把网站变成干净的 markdown，作为 MCP 服务器插进你的 AI agent，还能在 localhost 上应答 Firecrawl API。

Firecrawl Cloud。 托管版，Local 能做的事它都能做，而且规模更大、什么都不用跑；外加搜索和 Alexandria 里那 550 多个数据提供方。

自托管。 从 apps/api 部署完整服务器，带自己的队列、worker 和数据库。

三条路，同一个仓库，同一套 SDK。

而那句「Pst. Hey you, join our stargazers :)」还留在原文里——二十万星的项目，还是会用这种口气跟人说话。

三种形态，一张表

真正让我觉得这份文档老实的地方，是那张叫「什么在哪跑」的表。

能力 Local Cloud
抓取 markdown、HTML、原始 HTML、链接 加上结构化 JSON、摘要、截图、浏览器动作
爬取、地图、批量抓取 有 有
PDF 与 Office 文档 有 有，外加上传文件的解析
搜索 通过 Cloud，不需要账号 有
Alexandria 登录后通过 Cloud 有
Interact、Agent、监控 无 有

左边那一列，是一个二进制能做到的事。右边那一列，是一台机器加上一堆浏览器、模型和索引才能做到的事。

而这张表最诚实的一行，是搜索：Local 也能搜，但请求走的是 Cloud，而且不需要账号。

它没有假装本地能独立完成所有事。它把「哪一步必须出门」标出来了。

96% 和 3.4 秒：厂商数字该怎么读

云那一侧给了三个数。

覆盖 96% 的网页，包括 JavaScript 很重的页面和动态应用。

P95 延迟 3.4 秒，跨数百万页面统计，为实时 agent 和动态应用设计。

输出是 LLM 就绪的：干净的 markdown、结构化 JSON、截图，让 agent 少烧一点 token。

这三个数都是厂商自报的，文档里也没打算装成第三方评测——它把支撑数字的那篇文章链接放在括号里，等于说「过程在那儿，你自己看」。

读这种数字，有两个地方值得留意。

第一个是 P95。很多服务报平均值，而平均值是最容易被长尾拉平的指标：九十个请求两百毫秒，十个请求五秒，平均下来依然漂亮。P95 说的是「最慢的那百分之五」——而你真实使用时的体感，往往就由那百分之五决定。

第二个是「数百万页面」。样本怎么选的、页面类型怎么分布的、失败的重试算不算进去，这些都不在这段话里。所以 96% 这个数，能当方向看，不能当承诺用。

有意思的是，同一份文档里，本地版一个性能数字都没有。

因为本地版的速度取决于你的机器、你的 Chrome、你的网络。它没法给一个 P95，所以它干脆不给。

一份文档，在能吹的地方给了数字加出处，在不能吹的地方闭嘴。这个分寸感比数字本身可信。

那个 3002 端口

整套设计的关键，其实是一行不太起眼的命令：

它在本机的 3002 端口上，应答 Firecrawl 的第二版 API。而本地路由不需要 API key。

这句话的实际含义是：你为一个托管服务写的代码，可以在自己的笔记本上原样跑。

SDK 里改一个参数就行——把 API 地址指到本机的 3002 端口，剩下的不用动。抓取、爬取、地图，全部落在本地。

这是个很聪明的抽象。因为大多数「本地版」的做法是做一个精简客户端，接口不一样、能力不一样、返回值不一样，于是你的代码里长出一堆 if (isLocal)。

而这里的做法是：形态可以换，契约不变。

同一个 SDK，指向三个地方——本机的二进制、自己的服务器、官方的云。代码里只有一行不同。

这件事对一个要长期维护的项目来说，价值比任何单个功能都大。因为接口稳定，才有生态；接口一变，所有集成方都得跟着改一遍。

九种语言的 SDK，和一份被反复复用的契约

SDK 那一栏列了九种语言。

Python 和 Node 是一等公民，各给了一段能直接跑的示例。装完之后，那段示例演示四件事：抓一个页面、用 Agent 自己去收集、爬一个站、搜一次网。四个动作，正好对应四个最常见的用法。

剩下七种挂在表里：Go、Java、Rust、Ruby、.NET、PHP、Elixir。每种一行安装命令，加一个文档链接。

九种。

这个数字不是慈善，是契约稳定的副产品。

因为维护一份 SDK 的成本，主要不在写第一版，在跟着接口变化改。一个 API 如果每个月改字段，九份 SDK 就会变成九份负债——总有人用着三个月前的版本，然后提一个「为什么反序列化失败」的 issue。

所以一个项目敢同时挂九种语言，通常意味着两件事：接口定型了，而且边界清楚。

而文档里有一句话，把这九份 SDK 的价值又提了一层：它们同时支持云和本地，只要把 API 地址指到本机那个端口。

也就是说，这九种语言的绑定，不是九份云客户端，是九份「指向任意 Firecrawl」的客户端。

顺带一个巧合：列表里有 Rust SDK，而本地那个二进制也是 Rust 写的。同一个组织用同一门语言做客户端和服务端，通常说明他们真的在用自己发出去的东西。

一个会「偷偷上云」的本地工具，但它告诉你

这是我看这份文档时最想单独拎出来的一点。

Local 是本地优先，但有一个默认行为：如果一个单页抓取在本地加载不出来，它会被 Firecrawl Cloud 取回来，并在结果里标上 "source": "firecrawl-cloud"。

也就是说，它会出门。

但它做了三件事：

第一，标出来。结果里有一个字段告诉你这次是谁抓的。

第二，说明白。文档写了：这些云端调用不需要账号，但速率有限；firecrawl-local login 之后算到你自己的账号上。

第三，给开关。设一个环境变量 FIRECRAWL_CLOUD=off，所有东西都留在你机器上。

这三步的顺序很重要。它没有问你要不要上云，它默认上云并告诉你，然后把关闭的权力交给你。

对比一下另一种常见做法：悄悄重试到云端，失败了再报错，你永远不知道数据从哪来。或者反过来，纯本地，一遇到 JS 渲染的页面就返回一句「不支持」，让你自己去查为什么。

而这个方案承认了一个现实：本地的 Chrome 不是万能的，总有些页面在你机器上渲染不出来。与其返回失败，不如换一条路走，但把路线记在结果里。

对一个要把网页内容喂给模型的工具来说，这条「来源字段」其实很重要。因为你在做 RAG 或者做数据管道的时候，需要知道某一份内容是怎么来的——是本地渲染的，还是从别处取的。

不要 key，不要注册

这一节只有两句话，但可能是整份文档里商业意味最重的地方。

Firecrawl Keyless 每月给你一千个免费积分，不需要 API key，不需要注册，MCP、CLI、API 三条路都能用。

配套的是这条命令：

一行，装都不用装，直接吐出 markdown。

这个设计针对的是一个很具体的摩擦点：第一步。

大多数 API 服务的第一步是这样的：注册、验邮箱、进控制台、创建项目、复制 key、粘到环境变量、跑 demo。中间任何一步卡住，这个人就走了。而这里的第一步是：跑一行命令，看见结果。

把「注册」从第一步挪到第 N 步，是一个很朴素但很少被真正执行的增长策略。因为大部分公司舍不得——他们怕白嫖。

而一千个积分一个月，对一个想验证「这东西值不值得用」的人来说，够了；对一个已经天天在用的团队来说，远远不够。

于是它变成一个很干净的漏斗：先让你用起来，再让你付钱。

Alexandria：价格是工具的一部分

这是整份文档里我最感兴趣的一节，因为它给 agent 设计的东西，不只是接口。

Alexandria 是一个库，里面是 550 多个数据提供方：2.5 亿以上的人物、7500 万家以上的公司、4100 万篇以上的研究论文，加上专业索引和实时网页。通过一个 API、一个 MCP 或者一个 CLI 交付。

而它描述的那个机制，值得逐字读：

AI agent 会在自己的网页结果旁边发现一个工具，查看它的输入和价格，然后运行它，拿到结构化数据。发现是免费的，运行一个工具会消耗它上面标着的积分。

「查看它的输入和价格」。

这句话把一个通常只存在于人类界面上的东西，搬进了机器的调用链：价目表。

大多数工具市场是这么工作的：人类浏览、人类比价、人类点击。而 agent 没有这个环节——它只会调用它看见的工具。如果你把价格藏在文档第三页，它就会在预算之外反复调用，然后你在月底看到一张账单。

而 Alexandria 把「这个工具要花多少」写成了工具元数据的一部分。agent 在决定调不调用之前，可以先看一眼。

这个设计解决的是一个很新的问题：当调用方不是人的时候，定价该怎么表达。

顺带说，这也解释了为什么它强调「发现是免费的」。因为对一个 agent 来说，搜索工具这件事本身要花钱的话，它就不敢搜了。

Interact 与 Agent：从「抓」走到「做」

前面那些能力——抓取、爬取、地图、批量——都是「读」。

Interact 是「写」。

它的用法分两步：先抓一个页面，拿到一个 scrape id；然后对着这个 id 发指令。指令可以是自然语言，也可以是代码。

文档给的例子是打开一个电商站点，先搜「机械键盘」，再点第一个结果。

而返回里有一个字段叫 liveViewUrl——一个可以看着它操作的地址。

这个细节很小，但它是「自动化」和「看得见的自动化」的分界线。因为一个替你点按钮的东西，如果看不见它在点什么，你只敢让它跑测试环境。

Agent 那一层更彻底：你连 URL 都不用给。

描述你要什么，它自己去搜、去翻、去取。返回的是结果加来源。文档还给了结构化输出的路子——传一个 schema 进去，拿回来的是按 schema 组织的对象。

里面提到几个可调的东西：起始 URL、投入档位，以及一个叫 spark-2 的模型。

「投入档位」这个词挺有意思。它承认了一件事：这类任务没有标准答案，只有「愿意花多少」的取舍。找一家公司的创始人，搜三个页面和搜三十个页面，答案的置信度不一样，成本也不一样。

把这个选择交给调用方，而不是假装有一个最优解，是个成熟的做法。

注册这件事，现在可以交给 agent

有一段话，我读了两遍。

文档说：一个 AI agent 可以通过取一份入门技能文件，替它的用户注册并拿到 API key。

也就是说，注册这个动作，被设计成可以由机器执行的。

这句话背后的场景很具体：用户在 Claude Code 里说「帮我抓这个文档站」，agent 发现没有 key，于是它去取一份说明、按说明完成注册、拿到 key、继续干活。整个过程里，人只需要做那个真正需要人做的决定。

这是一个很小但很新的产品问题：当你的用户是一个 agent 的时候，你的注册漏斗长什么样？

传统的注册漏斗假设有一个人类在填表单、接验证码、读邮件。而 agent 不能接验证码，也不该替你点「我同意」。

所以这里能自动化的只有一件事：把注册流程写成机器能读的步骤，然后让人只保留那个真正需要人的决定。

我不知道这条路的边界在哪，但这个方向是对的。因为未来会有越来越多的服务，第一次被调用时，调用方不是人。

init 会改你的配置，所以它先备份

firecrawl-local init 做的事，是把本地服务作为一个 MCP 服务器，加进你机器上的 agent。

它会去找六样东西：Claude Code、Claude Desktop、Cursor、Windsurf、Gemini CLI、Codex。

而文档里那句话写得很克制：它在动手之前，会备份每一个配置文件。

一个工具要去改别的工具的配置文件，最该有的品德就是这个。

因为这类操作的风险不对称：改对了，用户什么感觉都没有；改错了，用户会花一个下午排查「我的 Cursor 为什么连不上模型了」。

顺带说两个门槛：那个 MCP 服务器本身需要 Node 22 以上；而本地的抓取要 Rust 和 C 编译器，macOS 上是装命令行工具，Debian 或 Ubuntu 上是装编译基础包。

它没有假装这两个依赖不存在。它把它们写在命令旁边。

而云那一侧，给 agent 的入口是另一条命令：一条 init 加上两个开关，就把全部的云工具挂进去，兼容 Claude Code、Antigravity、OpenCode 这些宿主。

任何 MCP 客户端也能手写一段配置接进来——跑 npx，加一个包名，把 API key 塞进环境变量。就这三行。

这里有一个很值得注意的细节，藏在本地那一节里：装好之后，抓取、爬取、地图、批量抓取这四个工具跑在你的机器上，而其余的工具走 Firecrawl Cloud。

同一个 MCP 服务器，工具列表是按能力拆开路由的。

这句话解释了很多事。为什么它敢说「插进你的 agent」——因为对 agent 来说，看到的就是一组工具，它不需要知道哪个在本地哪个在云上。而为什么它又说「其余走云」——因为搜索、Interact、Agent 这些能力，本来就没法塞进一个二进制里。

本地与云端的分界线，在这里从「部署方式」变成了「工具路由」。这是同一个决策的两种表达。

除了 MCP，还有一条给「把 Firecrawl 写进产品代码」的人准备的路：一份技能目录，一条 npx skills add 装上。仓库里也放着自己的那一份，CI 会把它镜像到目录里去。

从「让 agent 用」到「让 agent 帮你集成」，是两个不同的场景。前者是调用，后者是施工。

自托管：完整的服务器还在，但最新的不在里面

这一节很短，但信息量不小。

Local 是最省事的自托管方式。而如果你真想要那套完整的服务器——带队列、worker、数据库——它还在这个仓库里，可以跑在你自己的基础设施上。

部署形态是 Docker Compose，和 Redis、PostgreSQL、一个浏览器服务一起起来。仓库里还有一份文件，列出你检出那个版本对应的服务和设置；规模大一点可以从 Kubernetes 清单或者 Helm chart 起步。

然后是那句必须说清楚的话：Alexandria 跑在 Firecrawl Cloud 上，所以自托管的服务器不包含它。

这句话把开源边界画在了明处。

AGPL 给你的是爬虫、是解析、是队列、是那套 API。而 550 个数据提供方——那些需要签合同、需要维护索引、需要持续付费采购的东西——留在云上。

这不是藏私。这是唯一能成立的模式：一个靠采购和运营撑起来的能力，没法用一份仓库交付。

值得肯定的是它说出来了，而且就写在这一节的最后一段，不在某个定价页的脚注里。

许可、四个仓库，和一句「别给只读目录提 PR」

最后是两件治理上的小事。

许可切得很细。 主体是 AGPL-3.0，而 SDK 和部分界面组件走 MIT。

这个分法是有道理的：AGPL 管的是那个服务器——你要改它、要提供给别人的话，得开源；而 SDK 是给调用方用的，用 MIT 才能塞进任何商业项目里。

一个既想守住服务端、又想让人随便集成客户端的项目，基本只有这一种切法。

技能分在三个源仓库里，另有一个只读目录。 CLI 的技能放 CLI 那个仓库，构建和 SDK 的技能放这个仓库的 skills/ 目录，工作流的技能放第三个仓库。

而那个对外的技能目录是只读的——文档原话是：永远不要直接对它提 PR。

因为它是从三个源仓库同步过去的镜像。你给镜像提 PR，改完之后下一次同步就没了。所以它干脆把这条写在正文里。

一个项目愿意解释「为什么这里不能提 PR」，说明它被这件事烦过。

最后

回到那个反常的细节。

一个 TypeScript 项目，把本地版做成了 Rust 二进制。表面上看是技术选型，往深里看是一次产品分层：

能在你机器上做的事，就免费给你，做成一个不用注册、不用联网的二进制。

需要浏览器集群、需要模型、需要采购 550 个数据源的事，收钱。

而连接这两层的，是一个端口和一套没变过的 API。

这个分层的好处，用户能立刻感觉到：你今天只是想抓一个文档页，那就装个二进制，跑一行，拿到 markdown，全程没有账号、没有额度、没有账单。等你哪天要搜全网、要点按钮、要查一家公司的资料，再回头看那朵云。

坏处也有，而且它写在文档里：本地渲染不了的页面会去云端取，你得记得那个来源字段；自托管拿不到 Alexandria；装本地版要先有个 Rust 工具链。

一份把好处和坏处都摆在同一页上的文档，读起来是会让人多信一点的。

至于那二十万颗星——它们大概不是冲着「markdown 转换」来的。它们冲的是那件更朴素的事：终于有人把「让模型读网页」这件事，做成了一个可以调用的动词。
