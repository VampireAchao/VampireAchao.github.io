该用代码保证的事，别交给模型：Open Code Review 的分工表

先说三个熟悉的毛病

用通用 agent 做代码评审，几乎每个人都会踩到同样的三个坑。

第一，偷懒。 变更一大，它就只挑几个文件看，剩下的要么跳过，要么扫一眼就说「看起来没问题」。

第二，位置漂移。 它说「这里有空指针风险」，你点进去一看，那行是注释；它说第 42 行，实际在第 67 行。

第三，不稳定。 同一个 PR 跑两次，结论不一样；改一个字提示词，风格大变。而且你没法调试——输出的是一段自然语言，哪一步错了根本看不出来。

阿里巴巴这个项目对这三个毛病的诊断，只有一句话：纯语言驱动的架构，对评审过程缺少硬约束。

项目地址：https://github.com/alibaba/open-code-review

它的自我介绍是：一个 AI 驱动的代码评审 CLI。前身是阿里内部的官方 AI 代码评审助手，两年里服务了数万名开发者，发现了数百万个代码缺陷，在大规模验证之后开源。

这句话里的数字很有说服力，但真正有意思的是它给出的解法：混合架构。

分工表

它的核心哲学，可以压成一句话：确定性的工程和 agent 各干各的，干自己最擅长的。

哪些事必须「不能错」？四件。

精确的文件选择。 哪些文件该审、哪些该过滤，由一个确定的逻辑决定，而不是让模型自己挑。这一条直接掐死了「偷懒」。

聪明的文件捆绑。 相关的文件被打成一个评审单元——文档举的例子很传神：message_en.properties 和 message_zh.properties 应该捆在一起。每个包跑一个子 agent，上下文互相隔离。

细粒度的规则匹配。 规则不是一股脑塞进提示词，而是按文件特征匹配。文档还专门对比了一句：基于模板引擎的规则匹配，比语言驱动的规则指引更稳定、更可预测。

外部的定位与反思模块。 评论定位和评论反思是两个独立模块，专门用来提升 AI 反馈的位置准确度和内容准确度。

然后哪些事交给 agent？两件。

场景调优的提示词。 为代码评审深度优化的模板，效果更好，token 更省。

场景调优的工具集。 这一条的来历值得单说：它是从大规模生产数据里的工具调用轨迹中蒸馏出来的——包括调用频率分布、每个工具的重复率、新工具对整条调用链的影响。

也就是说，这个 agent 的工具箱不是「给通用 agent 的那一套」，而是从真实调用日志里长出来的。

那条分界线，画得比大多数产品清楚

我见过很多「AI + 规则」的产品，它们的做法通常是：让模型先判断，再用规则兜底。

这个项目的做法相反——把不该出错的部分，从模型手里直接拿走。

位置漂移是最好的例子。让模型输出「第几行」这件事，本质上是在让一个语言模型做坐标计算。它做得不差，但它会错，而且错得毫无规律。

而「定位」这件事，代码可以做得百分之百准确：文件是确定的、行号是可数的、diff 的偏移是可计算的。

于是它把定位拆成独立模块，模型只负责说「这里有问题，因为什么」，至于这句话最终钉在哪个位置，由工程逻辑算。

这个设计很像编译器：前端做语义分析，后端做地址分配。没人会让语义分析器自己去猜内存地址。

文件捆绑这件事，比看起来聪明

message_en.properties 和 message_zh.properties 捆在一起审——这个例子一秒钟就让人明白为什么。

因为这两份文件的问题永远是同一个：你加了 key，忘了加另一个；或者两个都加了，但翻译和行为对不上。分开审，两个 agent 各自看到一半证据，都只能说「看起来没问题」。

而捆在一起之后，还有一个更重要的副作用：每个包是独立的上下文。

这意味着两件事。一是大变更集不会把上下文撑爆——分而治之，每个包只看自己那一小块。二是天然支持并发——包与包之间没有依赖，可以同时跑。

一个设计同时解决了「上下文长度」和「吞吐」两个问题，这种便宜不常见。

基准：一个敢说自己召回更低的项目

基准那一节，开头就是一句不太像营销的话：

和通用 agent 相比，在同样的底层模型下，它的精确率和 F1 显著更高，token 消耗只有约九分之一，速度更快。

然后是那句关键的补充：它的召回率低于通用 agent——这是有意为之的取舍，偏向精确而非噪音。

这句话值得鼓掌。

所有做代码评审的工具，都面临同一个矛盾：报得多，人烦；报得少，漏。而大多数产品会选择模糊处理——既不给你召回率，也不给你精确率，只给你一句「更智能」。

这里直接把短板写在正文里，还解释了为什么这么选：评审意见的价值不在于「我提到了多少」，而在于「我提到的是不是真的」。一条误报的代价，是工程师花十分钟去确认它不存在——而这个成本乘以变更量，很快就超过漏报的期望损失。

基准本身也做得挺严肃：50 个热门开源仓库、200 个真实 PR、10 种编程语言、80 多位资深工程师交叉验证、1,505 条标注过的问题。数据集还单独放了出来。

两种执行模式，解决一个很现实的账

配置那一节有个细节，很多人会略过，但它很关键。

它明确区分了两种模式：

OCR 调模型。 ocr review、/open-code-review:review 命令、open-code-review 技能，用的都是 OCR 自己的 provider 配置——不是你 Claude Code 的团队版或专业版订阅登录。

宿主 agent 调模型。 /open-code-review:delegate-review 命令和对应的技能，用宿主 agent 已经配好的模型和认证，OCR 这边不需要任何 LLM 配置或凭证。

第二种模式叫「委托」。OCR 只负责文件选择和规则解析，实际的评审由你的编码 agent 自己完成。

这个设计解决了一个很实际的问题：有些人不愿意再开一个 API key。

而它没有把这件事藏起来，也没有含糊地说「支持你的订阅」，而是明确写了「这两条路用的是不同的账号体系」。这种把账算清楚的做法，比任何「无缝集成」的宣传都更让人放心。

生态：不只是个 CLI

文档目录列出的东西，说明它想当基础设施而不是一个脚本。

MCP 服务器，用来给评审 agent 接外部工具；CI/CD 集成，GitHub Actions、GitLab CI、GitFlic CI、Gerrit；会话查看器，能在浏览器里浏览和重放评审会话，把评论标成已修复或已忽略、并且在你处理时先隐藏它们；OpenTelemetry 集成，用于可观测性。

会话查看器那条尤其贴心。「标成已忽略、先隐藏」——这是真实评审流程里最需要的一个动作：有些意见你看过了，判断它不适用，但你不想每次打开都再看到它。

一个工具愿意为「我已经否决过这条」做一个状态，说明它真的被用在有几百条评论的 PR 上过。

内部工具开源，通常意味着它已经扛过真实的烂摊子

这份文档有一句话说得挺轻：在「大规模验证」之后，我们把它孵化成了开源项目。

这句轻描淡写背后是两年和数万名开发者。

这两件事的组合很关键。一个内部工具要活过两年，得面对那些只有真实环境才有的问题：几千行的巨型 PR、生成的代码、vendored 依赖、带二进制文件的提交、一半是重命名的 diff。

而它现在能开源，说明这些坑基本都填过了——至少填到了「社区拿去用不会第一天就崩」的程度。

这和「先做开源项目再找用户」是两条完全不同的路。后者的文档里通常有一种乐观的空白：它假设输入是干净的、PR 是合理的、用户是有耐心的。

而这份文档的起点是一句诊断——纯语言驱动缺少硬约束。这是一句只有被真实场景教训过的人才说得出来的话。

最后

回到开头那三个毛病。

偷懒、漂移、不稳定——它们的共同点不是模型不够聪明，而是我们把太多「本该由代码保证」的事，交给了语言模型。

Open Code Review 的答案很朴素：先分清哪些事不能错，把那些事写成确定性的代码；剩下的才交给 agent，并且给它一套从真实调用数据里蒸馏出来的工具。

这个分工听起来不高级，甚至有点保守。但代码评审这件事，本来就该保守——你不是在找一个「有创意的意见」，你在找「这里会不会出事」。

至于它把召回率更低这件事写在正文里，那大概是这份文档里最像工程师的一句话：我们知道自己漏，我们选择不吵。

在一个到处都在比谁报得多的行业里，这个选择挺难得的。
