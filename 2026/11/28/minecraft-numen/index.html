天时不如地利，地利不如人和。——《孟子・公孙丑》

一次调用跑完几十步：Minecraft 里那个智能体在写程序，不在点按钮

先说那个名字

「言出法随」。

这四个字在中文里的意思是：话一出口，规则就随之生效。

用来命名一个「你说一句，它去做」的智能体，实在贴切得过分。而它的英文名是 Numen——拉丁语里的「神意」「守护灵」，一个住在某处、有自己意志的东西。

中英文两个名字，其实说的是两件事：中文说的是效力，英文说的是居住。

而它两个都做到了。它住在游戏里，作为模组存在；而它执行你话的方式，比「听一句做一步」要复杂一点。

项目地址：https://github.com/Dwinovo/minecraft-numen

描述写得很干脆：Numen 是你在 Minecraft 里的个人智能体。它作为模组活在游戏之中，不断探索这个世界，自己做决定，采取行动把事情做完。

三层，最上面那层在写程序

整个架构被切成三层，自下而上。

最底层是 Minecraft。 智能体在里面操纵一个真实的玩家。

中间层是给大语言模型的接口。 主体是一套由原子动作构成的 Lua API，涵盖感知、移动、挖掘、建造、交互。其他模组也能通过插件接进来。另有一小部分 Java API 以工具调用的形式提供，比如加载技能。

最上层是大语言模型。 它编写在沙箱里运行的 Lua 程序，自由组合那些原子动作，一次调用就能连续完成几十个步骤。

画成图是这样：

最后一句话，是这一整套设计里最关键的一句。

因为它说明这个 agent 不是「调一次工具、看一眼结果、再调一次」那种循环。它是「写一段程序，交给沙箱跑完，回来看结果」。

这两件事的差别，比它听起来大得多。

为什么是程序，不是工具调用

想象一个最基础的任务：做一把木镐。

在人的脑子里，这是三句话：找棵树，砍木头，做。

落到游戏里，它是几十个动作：走到树前、对准某一块原木、按住挖掘、等它掉、捡起来、再挖两块、打开背包、把木头放进合成格、取出木板、把木板放进合成格、取出木棍、打开工作台、按配方摆好、取出木镐。

如果每一个动作都是一次工具调用，那就是几十次模型往返。每次往返都有网络延迟，都要把上下文重新发一遍，都要重新计费。

而这只是做一把木镐。

所以这套架构的选择是：让模型写程序。

模型不需要真的「看见」每一步。它需要知道有哪些原子动作、每个动作的参数是什么、失败会返回什么。然后它写一段 Lua，把「走过去、挖三块、合成、再做镐」写成一个循环加几个判断，交给沙箱。

沙箱跑完，回来一个结果。而这一次往返，覆盖了几十个动作。

一次往返，几十个动作。

这个思路在 agent 圈子里有个名字，叫「用代码当动作」。它的好处不只是省往返——代码本身能表达循环、条件、重试。而这些恰好是「挖矿」这件事需要的：挖到石头就换镐、背包满了就丢掉圆石、天黑就回家。

用自然语言描述这些分支很啰嗦，用代码写出来是三行。

为什么是 Lua

让模型写代码，第一件事是选一门语言。

常见的选择有三个方向：Python，因为模型最熟；JavaScript，因为生态最大；Lua，因为它最小。

这里选了 Lua。

从「让模型写」这个角度看，小是一个巨大的优势。因为模型的出错率，大致和语言的表面积成正比。Python 里有列表推导、装饰器、生成器、async，每一个都是它能写错的地方；而 Lua 里主要就两样东西——表，和函数。绝大多数逻辑都能用这两样表达。

语法小还有第二个好处：沙箱好做。Lua 的标准库本来就极简，把它裁到只剩需要的几个函数，比裁一个带文件系统、网络、进程的运行时容易得多。而沙箱越干净，「模型写的代码能干什么」这件事就越可枚举。

第三个好处是嵌入。Lua 从一开始就是为「嵌进别人的程序里」设计的，在 JVM 上有成熟的实现。对一个模组来说，这是硬需求。

顺带说，Lua 在 Minecraft 模组圈子里也不算陌生——那些游戏内的电脑模组早就用它当脚本语言了。

至于作者具体为什么选它，文档没说。但把这三个理由摆在一起，这个选择几乎是必然的。

沙箱不是保险，是边界

「在沙箱中运行」这几个字，值得单独拆开。

因为模型写出来的 Lua 是不可信代码。它是根据一句自然语言现场生成的，没有人审过，也不可能每一段都审。你不会想让这样一段代码拿到整个 JVM 的权限——它能读文件、能开网络、能反射调用任何东西。

所以沙箱的第一层意义是安全：你只能调用我给你的东西。

但沙箱还有第二层意义，而这一层更影响产品：它同时也是能力边界。

模型能做什么，等于「沙箱里有什么」。它不能凭空创造能力，只能组合已有的动作。所以「原子动作」这份清单，其实就是这个智能体的全部本事。

这也让插件这件事变得很清楚：注册一个新的 Lua API，不是加一个功能按钮，是给模型扩词汇。词汇多了，它能写出来的程序就多了。

一个装了车万女仆插件的世界，和一个没装的世界，对这个智能体来说不是「多了个模组」，是「多了几个动词」。

不过这里有一个必然要处理、文档却没有展开的问题：死循环。

模型完全可以写出一段 while true do end，或者一个走不到终点的寻路。这类沙箱必须有一个执行上限——多少条指令、多少秒、多少次动作调用——否则一次生成就能把游戏卡死。

文档没写它的限制是多少。但任何让模型写代码的系统，都在这一处藏着它真正的工程水准：限得太松会卡，限得太紧会把正常的长任务掐断。而「一次完成几十个步骤」这个卖点，恰好要求上限不能太小。

这两件事怎么平衡，大概只有作者知道。

原子动作，其实是一份词汇表

「原子」这个词用得很准。

因为它要求每个动作都不可再分，而且语义清楚：参数是什么、成功返回什么、失败返回什么、失败了能不能重试。

太粗不行。如果只有一个叫「建房子」的动作，模型就没法组合——它只能祈祷这个动作能应付所有情况。

太细也不行。如果动作细到「把手抬高一度」，一段砍树的程序会长到超过上下文长度。

所以设计这套 API，本质上是在设计一门语言的粒度：刚好够表达意图，又不至于让程序失控。

而它覆盖的五类——感知、移动、挖掘、建造、交互——恰好是一个玩家能做的事的完整分类。

这五类也是写循环的原料。感知提供条件，移动和挖掘是动作，建造是组合，交互是跟世界打交道。模型写的程序，基本就是在用这五类东西拼出「先这样，如果那样，就改成那样」。

一次跑几十步的另一面

写程序这个选择，有一个内在的代价，值得说清楚。

工具调用是「走一步看一步」：每做完一个动作，模型都能重新评估，发现不对就换方案。它的好处是灵活，坏处是慢。

写程序是「想清楚再动手」：模型把整段逻辑一次性写出来，交给沙箱跑。它的好处是快，坏处是——如果第四步就错了，后面几十步全是白跑。

而且模型在程序运行期间是「闭眼」的。它没法因为「前面有只苦力怕」而临时改主意，除非它在程序里已经写了这个判断。

所以这类架构通常要靠两样东西补偿：一是程序要能返回「执行到哪一步、为什么停」，让模型下一次能修；二是动作本身要有防御性，比如「走过去」这个动作在遇到障碍时会失败而不是硬撞。

文档没有展开这些细节。但这也是这类设计真实的样子：它把「多次往返」的成本，换成了「一次写错」的风险。 而这个交换划不划算，取决于模型写代码的能力，和这套原子动作好不好用。

换句话说，这个模组的体验上限，不取决于它的模型多强，取决于它的 API 设计得多像一门好用的语言。

它操纵的是一个真实的玩家

这一句藏在架构描述里，很容易被读过去：智能体操纵的是一个真实的玩家。

不是一只特殊的 NPC，不是一个有上帝视角的实体，是一个玩家。

这句话的后果，比它的字数重。

因为「玩家」意味着它受同一套规则约束：它有背包，背包会满；它会掉血，掉进岩浆会死；它要吃东西，不然会饿；它走路要一格一格走，不能瞬移；别的玩家能看见它、能打它、能跟它交易。

也就是说，这个智能体没有作弊通道。它不能直接调用「把这块石头变成圆石」的函数，它得真的拿着镐去挖。

这个选择让事情变难了，但也让事情变真了。因为它做的每一件事，都是这个游戏允许一个玩家做的事。它的能力上限，就是玩家的能力上限。

对一个要「在游戏里长期存在」的智能体来说，这个约束反而是一种诚实：你不是在模拟一个玩家，你就是那个玩家。

插件：让智能体学会别的模组

中间那一层最聪明的地方，是它开放了注册。

任何开发者都可以通过插件，向言出法随注册新的 Lua API，供模型调用。于是智能体的能力边界，不再由这个模组自己决定，而由你装的模组包决定。

仓库的 plugins 目录里已经有两个现成的例子。

一个是「是，史蒂夫模型」，一个换皮肤的模组。接进来之后，模型可以通过它的 Lua API 切换自己的皮肤——也就是说，这个智能体能给自己换衣服。

另一个是「车万女仆」。接进来之后，模型可以通过它的 Lua API 驯服女仆。

第二件事听起来像个玩笑，但它其实是一个很好的测试用例：驯服女仆这类操作，通常不是一次交互就能完成的，它涉及位置、条件、动作顺序的组合。而模型写出来的那段 Lua，就是在组合它们。

文档还说了，这些插件可以作为编写插件的参考模板。

这句话的意思是：生态的入口不是一份 API 文档，是两个能跑的例子。对开发者来说，后者比前者好用得多，因为你总能找到一个最像你需求的那个，改。

把大脑接到外面

有一段设计，我觉得是整份文档里最实用的一处。

言出法随可以整体作为一个 MCP 服务器，由外部的智能体直接驱动——Claude Code、Codex、Cursor 之类任何支持 MCP 的客户端。

这时候，推理和 token 都算在外部智能体身上。

于是你有了一条很划算的路：用订阅套餐驱动它，而不是按量付费。

文档自己也是这么说的：通常比按量调用 API 更划算。

这句话背后是一个很现实的账。按量调用，一次长任务跑下来，token 账单是实打实的。而订阅套餐是包月的，你已经在付了，额度闲着也是闲着。

于是这个模组变成了一个「消耗订阅额度的容器」——你让 Claude Code 通过 MCP 去指挥一个 Minecraft 角色砍树。

这件事有点荒诞，但它很聪明。因为它在不改变任何东西的前提下，把两种计价模型接在了一起。

而代价也写清楚了：外接大脑模式下，人设不生效，对话上下文也不会存在模组内部。想保持人设，就写进外部智能体自己的提示词里。

换句话说，接管之后，它的「人格」由外部那一层负责，它只剩下身体。

一个有皮肤、有声音、有群聊的智能体

设置页那几项，拼起来是一个很具体的东西：一个有身体的、能被看见的、能社交的智能体。

皮肤。 把 PNG 放进配置目录的皮肤文件夹，在编辑卡里选一张给它穿上。第一次用到时经由第三方服务签名——因为游戏客户端只认签过名的皮肤——签过的不再重复签。

语音。 可以配置语音输入和语音输出，让它能听会说。

人设。 内置几种简单的，也可以写任何你喜欢的。

群聊。 把不同智能体的头像拖到一起，就建立了一个群聊。在群里可以 @ 某个成员让它回复，也可以不 @ 任何人、向全体广播。

最后这一项最有意思。因为它意味着你可以同时召唤好几个智能体，让它们待在同一个世界里，然后看它们互相说话。

一个会 @ 别人的 agent，和一个只会回答你的 agent，是两种东西。前者的行为空间里多了一整个维度：它可以对别的智能体施加影响。

而这件事在联机服上会变得更有意思。每个玩家带着自己的 key、自己的智能体、自己的账单；这些智能体在同一个世界里活动，各有各的皮肤、各有各的人设。它们在聊天框里互相 @，说的话又各自要消耗各自主人的额度。

一个小社会，账目分得很清。

至于人设那一项，在这个架构里的位置也很明确：它不是装饰，它是提示词的一部分。所以外接大脑模式下它会被摘掉——因为那一层归外部智能体管了，模组不越界去替它设定人格，也不替它保存记忆。

拿走人设、拿走上下文，只留下身体和动作。这个切割挺克制。

这已经不太像「工具」了，更像在养一群有名字、有皮肤、会互相喊话的东西。

它的交互假设你正在跑

按键表只有四行，但四行都在说同一件事。

G，打开面板。Y，不打开面板，直接说一句话。按住 R 加滚轮，在多个智能体之间切换对话对象。按住 V，语音输入，松开就发。

注意最后那两个字的说明：不影响 WASD 移动。

这一句把整个产品的使用场景讲清楚了。它假设你不是坐在桌前管理它，你正在游戏里跑——可能在被僵尸追，可能在搭脚手架，可能在矿洞里举着火把。

所以「打开面板」这个动作，在游戏里是有成本的：它意味着停下来。

于是有了 Y。不打开面板，说一句就走。它把「跟智能体说话」这件事，压到了一次按键的长度。

而 V 更彻底：按住说话，手还在 WASD 上。这是唯一一种不打断移动的输入方式。

至于 R 加滚轮——用滚轮切换对话对象，这个手势在游戏里通常用来换武器。它借了一个你已经在做的动作，来干一件新的事。

四个按键，没有一个是「打开一个窗口然后点几下」。这不是巧合，是因为设计者知道，在游戏里，任何需要停下来的操作都会被跳过。

顺带说，这个模组发在 CurseForge 上，在启动器里搜名字就能装。这个分发方式和那张版本表是同一枚硬币的两面：它接受「玩家不会读文档」这个现实，所以把安装压成一次搜索，把兼容压成一张矩阵。

装完进游戏，按 G，填 key，就能说话。中间没有第四步。

十三个版本，三种 Java

安装那一节的表格，是这个项目里最不浪漫的部分。

三个大版本段，十三个 Minecraft 版本：

1.20.1、1.20.2、1.20.4，Fabric 和 Forge，Java 17。

1.20.6、1.21、1.21.1、1.21.4、1.21.5、1.21.8、1.21.10、1.21.11，Fabric 和 NeoForge，Java 21。

26.1.2、26.2，Fabric 和 NeoForge，Java 25。

十三个游戏版本，两到三种加载器，三种 Java 运行时。

这张表说明了一件事：在 Minecraft 生态里，一个模组要能用，就得跟着游戏的版本走。因为游戏内部的映射、渲染、网络协议、注册表全在变，跨版本复用代码的成本高到不现实。

而这张表背后是十三套构建、十三套测试、十三套「这个版本上那个 API 改名了」的修补。

而且这不是「复制粘贴十三份代码」那么简单。Minecraft 每次大版本更新，内部的类名映射、渲染管线、网络包结构都可能变；不同加载器的注入点也不一样。所以十三套构建背后，是十三份需要分别验证的行为。

三代 Java 也不是它自己选的。1.20 那一代跑在 Java 17 上，1.21 那一代升到 21，最新那一代到 25——是游戏自己换了运行时，模组只能跟着换。

玩家看到的是一行「搜索 Numen 下载即可」。作者看到的是这张表。

那个「安全」的回答很短

常见问题里，第一条是关于 API key 的。

回答很干脆：安全。

理由有三句：智能体的推理发生在你自己的客户端上；key 只保存在本地，直接发往你选择的模型服务，不经过任何第三方服务器；也不会上传到游戏服务器。

三句话，把数据的路径划清楚了。

第二条问联机服能不能用。答案是能：双端模组，服务端和客户端都装即可，每位玩家用自己的 key，驱动属于自己的智能体。

这个设计很自然，但也挺考验人：一个服务器上可能有二十个玩家，二十个智能体，二十个 key，二十份账单。而模组本身不碰任何一份。

第三条问要不要花钱。模组开源免费，模型费用是你自己的。

三条回答加起来，是一个很清晰的责任边界：软件是我的，账和 key 是你的。

顺着这条边界往下看，会发现它有几件事是故意没做的。

没有内建模型。它不捆绑任何一家服务商，只提供两种协议和一堆预置选项，剩下的你自己填。

没有账号体系。它没有注册、没有登录、没有云端配置同步。你的设置就在你的客户端里。

没有中转服务器。key 直接发给你选的那家，中间没有人代收。

这三件事如果做了，会方便很多——也会让「安全」那个回答变得需要解释。而它选择了不做，于是那个回答可以那么短。

有时候一个产品的可信度，来自它放弃了哪些本来可以顺手赚的钱。

许可切了三刀

最后的许可，切得比大多数项目细。

代码走 LGPL-3.0。 这是 GPL 里偏宽松的那一版：你改了模组本体，改动要开源；但别人链接它、在它之上构建，不必跟着开源。对一个要被大量模组包集成的项目来说，这个选择挺合适——保住了核心，又没有把生态锁死。

但通过 API 使用本项目的插件，不受此限。 这句话很关键：你可以写一个闭源的插件，注册自己的 Lua API，卖给服务器，不必开源。

这是一个刻意的例外。因为插件生态要长起来，就不能逼每个插件作者都开源。而模组本体保持 LGPL，保证了核心不会被私有化。

截图、演示动图和架构图走 CC BY 4.0。 可以用来写文章、做视频，署名就行。

其余美术资源保留所有权利。 模型、贴图、logo 不在开放范围内。

三刀切下去，边界很清楚：代码开源但核心不外流，接口开放且不株连，图可以转载，画不能拿走。

最后

回到那个名字。

「言出法随」这个词，描述的是一种权力：你说什么，世界就变成什么。

而这个项目实现它的方式，恰恰是反过来的：它不给你权力，它给你一个遵守规则的玩家。

你说「帮我建个小屋」，它不会凭空生成一栋房子。它会写一段程序，让那个玩家去砍树、去合成、去一块一块地放。天黑了它可能还没建完，掉进水里它可能会淹死。

这听起来像是一个很差的实现。但它其实是唯一诚实的实现——因为在一个有规则的世界里，智能体要真的做事，就只能真的做事。

而它把「真的做事」这件事的效率问题，交给了一段程序去解决：一次调用，几十个动作，一个沙箱。

六百多颗星，一个中文名字，一个英文名字，十三套构建，还有两个能换皮肤和驯女仆的插件。

一个很小的项目，做了一件挺大的事：让一个语言模型，在一个它无法作弊的世界里，学会怎么用一段程序代替一双手。
