吾生也有涯，而知也无涯。——庄子

一份 Markdown，两个方向：Stitch Skills 把「设计」变成了可以搬运的东西

先说一件反常的事

「设计转代码」这件事，工具已经做了一轮又一轮。

截图进去，组件出来；Figma 图层进去，React 文件出来。方向永远是单向的：从设计到实现，从人到机器。

而这套技能里，有一条反过来的路。

它能把一个已经上线的前端应用，反向拆回设计系统：扫一遍源码，抽出一份设计规范；或者把一个跑在 localhost 上的页面，抓成一份自包含的静态 HTML；再或者，把整个前端代码库上传到设计工具里，变成一个可以继续编辑的设计稿。

于是这条路变成了双向的。

项目地址：https://github.com/google-labs-code/stitch-skills

它是 Google Labs 出的一套 agent 技能，配 Stitch 那个设计工具用。描述写得很直白：一套为 Stitch MCP 服务器设计的 agent 技能库，每个技能遵循 Agent Skills 开放标准，兼容 Antigravity、Gemini CLI、Claude Code、Cursor 这些编码 agent。

而两个方向之间，跑的不是代码，也不是图片。

是一份 Markdown。

十六个技能，三个插件

整个仓库按用途分成三个插件。

设计。 六个技能：代码转设计、生成设计、管理设计系统、抽取设计规范、抽取静态 HTML、上传素材。

构建。 五个技能：转 React 组件、转 React Native、生成 Remotion 走查视频、shadcn/ui 集成指导、转 React 加 Vite 的仪表盘。

工具。 五个技能：从设计项目生成设计规范、增强提示词、生成站点宪法、一句话生成多页网站、生成「高级感」设计规范。

六加五加五，十六个。

十六个技能听上去不多，但每一个都对应一个具体的动作，而且都配了可以直接照抄的提示词示例。比如：

「把这个登录页加上记住我，按钮改成蓝色。」

「生成首页的三个变体，暗色模式，高密度布局。」

「把 /src 扫一遍，把设计系统抽到 .stitch/DESIGN.md。」

这些句子读起来像人在跟同事说话。而这恰好是这类技能该有的样子——它们不是命令，是能被理解成任务的描述。

前提：这些技能是操作手册，不是独立工具

安装之前有一节叫「前置条件」，只有一段话，但它是理解整个仓库的钥匙：

这些技能需要 Stitch MCP 服务器在你的 agent 环境里配置好并且跑起来。

也就是说，这十六个技能本身不干活。它们不会帮你画图、不会帮你转代码、不会在本地跑一个模型。它们做的是：告诉 agent，怎么按正确的顺序去调用一个远程服务。

看那个代码转设计的描述就明白了：通过「抽 HTML + 建设计系统 + 上传」三步完成。三个动词，三个工具调用，顺序不能乱。技能的价值就在于把这个顺序写死。

所以文档里那句警告也就说得通了：这些技能之间有依赖，你要是挑着装，得自己把依赖补齐。

因为一个技能可能要用到另一个技能产出的中间物。比如先生成一份设计规范，再拿它去转组件——你把后半段单独装上，它就会找不到输入。

顺带说一个很有生活气息的细节。前置条件那一节里，除了正式说明，还有一句提示：如果文档站上的某个链接跳转错了，把目标路径贴回同一个域名下打开。

这句话的信息量在于：它知道自己的文档站存在跳转问题，于是顺手给了一条绕过办法。一个愿意教用户「怎么绕过我们的网站」的项目，通常是被自己人烦过很多次的。

反向那条路，才是最有意思的

三个技能构成了那条反向的路。

代码转设计。 把一个 React 或 Vue 的前端代码库，通过「抽 HTML + 建设计系统 + 上传」变成 Stitch 里的一个设计项目。示例提示词里带了一个项目名，叫「Dashboard-Migration-2026」。

这个名字把用途说透了：迁移。

一个团队要把老系统换一套设计，最常见的起点是什么？不是白纸，是那套已经跑了很多年的界面。设计师要重新画一遍，工程师要对着旧页面解释「这个间距是 12 还是 16」。而如果能把现有前端直接变成一个可编辑的设计稿，讨论就有了共同的参照物。

抽取设计规范。 扫源码，抽出一份 DESIGN.md。

这件事的难点不在于读颜色值，而在于判断哪些值是「设计系统的」，哪些是「随手写的」。一个三年的项目里，同一个蓝色可能有七个变体，其中六个是历史遗留。抽规范的过程，本质上是一次考古。

抽取静态 HTML。 从一个正在跑的页面抓一份自包含的 HTML，把 CSS 和图片全部内联进去。

这个技能解决的问题很朴素：你要给设计工具看一个页面，但它需要的是一个文件，不是一个网址。而很多页面的样子，只有跑起来才有——它依赖接口、依赖状态、依赖登录。

所以先跑起来，再抓下来。

DESIGN.md 是整个生态的货币

把这十六个技能连起来看，会发现中间有一个东西反复出现：DESIGN.md。

三个技能在生产它：从代码抽、从设计项目生成、按「高级感」标准生成。

一个技能在上传它，并把它当成主题应用到所有屏幕上。

两个技能在消费它：转 React 组件时要求「设计 token 一致」，转 Vite 仪表盘时直接说「用我们的 DESIGN.md」。

也就是说，这套工具真正在传输的东西，不是代码，不是截图，是一份用文字写的设计规范。

这个选择值得停一下。

因为设计和代码之间最难的翻译，从来不是像素值。是意图。为什么这个按钮是圆角十六而不是十二？为什么这个标题用这个字重？为什么这一屏要用留白而不是分割线？

一份设计稿传不了这些。一张截图更传不了。但一份 Markdown 可以——因为它就是文字，而文字恰好是唯一一种人和模型都能读、都能改、都能版本管理的格式。

于是设计系统变成了一个可以被 diff 的文件。

这件事的工程意义，比它听起来大。因为一旦设计规范是文本，它就能进代码仓库、能被 pull request 评审、能跟着分支走、能在冲突时手动合并。设计师改一行色值，工程师在 diff 里看得见。

而它同时也是一个赌注：赌「设计」这件事里，有足够大的一部分可以被写成规则。

一个技能，四个文件夹

整个仓库的形状是这样：

三层目录，十六个文件夹。每个文件夹里，又是同样的四层。

仓库里规定了每个技能的结构，只有四层：

SKILL.md。 文档自己的说法是「agent 的任务控制中心」。

scripts。 「可执行的强制者」——校验和联网。

resources。 「知识库」——检查清单和风格指南。

examples。 「黄金标准」——语法上一定正确的参考样本。

这四个文件夹，对应四种完全不同的东西：指令、执行、知识、样本。

而第二个最值得说。它不叫「脚本」，叫「强制者」。

这个词说明作者对一件事有清醒认识：光靠文字提示，管不住 agent。

你可以在 SKILL.md 里写「生成组件时必须使用设计 token」，但模型可能忘、可能偷懒、可能觉得这次特殊。而一个校验脚本不会忘——它跑一遍，不合格就报错。

所以每个技能都带了自己的「执行层」。这跟很多技能包的差别在于：那些包只有文字，这个包里有能跑的东西。

第四个也很有意思。「黄金标准」不是「示例」，是语法上一定正确的参考。这个限定词很关键：示例的作用不是教你怎么写，是给模型一个可以模仿的正确形状。

校验被写进了流程

「自动校验」这个词，在这份文档里出现了不止一次。

React 组件那个技能写的是：转成组件系统，带自动校验和设计 token 一致性。一句话生成网站那个技能写的是：带自动校验。而每个技能的目录里，都躺着一个 scripts 文件夹，文档管它叫「可执行的强制者」。

三处指向同一件事：这个仓库不相信「生成完就完事」。

这个不信任是有道理的。设计转代码最容易犯的错，不是语法错误——语法错了编译器会拦。它犯的是另一种错：看起来对，但不符合设计系统。颜色差一个色号，间距差四个像素，圆角从十六变成十二。

这类错误没有任何工具会报。人眼看不出来，测试测不出来，等到三个月后设计师打开页面，才发现整站有十七种灰。

所以校验要看的东西很具体：token 有没有用、用对没对。而它被写成了脚本，不是写成了叮嘱。

这大概是整套技能里最不性感、也最实用的一个决定。因为一个 agent 能记住多少条规矩，取决于上下文有多长；而一个脚本能检查多少条规矩，取决于你写了多少行。

前者会忘，后者不会。

四种装法，和一段列满「哪里会坏」的说明

安装这一节，是这个仓库最不像营销文案的地方。

Codex： 加一个插件市场，然后按需装三个插件。命令行里带了一串 --sparse 参数，只把需要的目录拉下来，克隆更快。文档还很实在地加了一句：这些参数是可选的，不加就拉整个仓库。

Claude Code 和 Cursor： 一条 npx plugins add，指定作用域和目标。一个装进当前项目，一个装进当前工作区。

两条命令的差别只有两个参数，但这两个参数恰好是两家宿主的心智模型差异：Claude Code 认为「项目」是单位，Cursor 认为「工作区」是单位。

选择性安装： 只想要某几个技能，用 npx skills add。但文档用了一个警告框提醒：这些技能之间有依赖，你要挑着装，得自己把依赖补齐。

OpenCode： 手动。

而 OpenCode 那一段，是整份文档里我最想推荐的部分。因为它没有写「也支持 OpenCode」，它写的是在 OpenCode 上哪里会坏：

OpenCode 不用那套插件市场，所以要手动把技能文件夹拷到它能发现的位置。

OpenCode 要求技能名是小写短横线格式、而且必须和目录名一致。所以那些用 stitch:: 命名的技能，得先改名才能被加载。

额外的 frontmatter 字段，比如允许使用的工具列表，会被忽略。

技能说明里写的工具名可能和 OpenCode 的内置工具不一样，一个叫 web_fetch，一个叫 webfetch。给 OpenCode 改技能的时候，要用它那一套名字。

四条，每一条都是一个具体的坑。而它选择在安装文档里把坑列出来，而不是让你装完之后自己发现。

这种写法有一个隐含的自信：我知道我的东西在别的平台上不是无缝的，我把差异写清楚，你自己判断值不值得装。

一个 :: 带来的麻烦

顺着上面那条，有个细节值得单独说。

十六个技能里，八个带 stitch:: 前缀，八个不带。

带前缀的是设计插件那一整组，加上构建插件里的 React 两个。不带的是 Remotion、shadcn/ui、Vite 仪表盘，以及工具插件的全部五个。

同一套东西，两套命名。

从工程角度看，加前缀是对的：技能是按话题自动触发的，一个项目里可能同时装着好几个来源的技能，同名就会打架。加个命名空间等于给它们分了姓氏。

但问题是，这个标准的命名约定还没统一。

:: 在有些宿主里是合法字符，在有些宿主里不是。于是同一个技能，在 A 家里叫 stitch::react-components，到了 B 家必须改名成 react-components 才能加载。改完之后，技能内部如果引用了自己的名字，又得跟着改。

一个标准成熟与否，往往不看它的核心概念有多好，看它的边界情况有没有约定。命名就是最典型的边界——它是每个技能的第一行，也是最容易被忽略的一行。

现在这个仓库的做法是：在自己的生态里用前缀，在别人的生态里写清楚「你得改名」。这是务实的，但也说明标准还在半路上。

六个宿主，一个格式

这份文档开头点名了六个宿主：Codex、Antigravity、Gemini CLI、Claude Code、Cursor、OpenCode。

六个，来自好几家互不相干的公司和项目。

而它们能读同一套技能，靠的是一件很朴素的事：技能就是一个文件夹，里面有一个 SKILL.md。

没有私有格式，没有编译产物，没有需要注册的账号。你把文件夹放到宿主认的路径下，它就认。这也是「Agent Skills 开放标准」这句话的实际含义——标准定在了文件系统这一层，而不是 API 这一层。

这个选择的好处，现在能看出来了：一个技能写一次，六个地方能用。管你用的是哪家的 agent，技能本身的写法不变。

而代价，恰好就是上一节那些麻烦。因为标准只约定了「文件夹里有什么」，没约定「名字能不能带冒号」「工具叫什么名字」「frontmatter 允不允许额外字段」。于是每一处模糊，都变成一次手动适配。

这也解释了为什么文档里专门为 OpenCode 写了一大段。它不是偏心，是因为 OpenCode 恰好是那个最不按套路来的样本——它不用插件市场，不用那套安装器，还额外要求命名规范。

一个标准能不能活下去，就看它愿不愿意为最不配合的那个实现，写清楚怎么接。

工具插件里，藏着三个有意思的东西

那五个工具类技能，名字都很朴素，但思路不太一样。

增强提示词。 把「做一个设置页」这种话，变成一段带 UI/UX 关键词的、Stitch 能听懂的描述。

这个技能存在的理由是：设计工具的输出质量，取决于输入的精度。而人的输入天然是含糊的——不是不会说，是不知道该说到多细。

站点宪法。 从一段项目描述或需求里，合成一份 SITE.md，作为「构建循环」的约束。

「宪法」这个词选得很妙。它暗示这份文件不是需求文档，是判据——后面每生成一个页面，都要拿它来对照。

反通用。 这个最有性格。它的描述是：生成执行「高级、反通用」UI 标准的 DESIGN.md，配的是严格排版和校准过的颜色。

「反通用」这三个字，其实是在跟一个具体的敌人作战：那种一眼就能认出来的、AI 生成的界面——紫蓝渐变、Inter 字体、内容区三张卡片。

而这个技能的做法不是给一堆禁令，是直接改产出物——它生成的那份 DESIGN.md，本身就是一份「不要长成那样」的规范。规范一旦进了仓库，后面所有组件生成都要受它约束。

用文件治文件，比用嘴治模型靠谱。

那个生成视频的技能

构建插件里有一个技能，和「把设计变成代码」完全不是一类事：

用 Remotion 从 Stitch 项目生成走查视频，带平滑转场和缩放。

输入是一个设计项目，输出是一段视频。

这个技能的存在，说明了一件事：设计稿的最后一公里不是代码，是说服。

因为你把一套新界面交给老板、交给客户、交给投资人时，静态图的说服力有限。他们想知道的是「用起来是什么感觉」——从首页滑到详情页，弹窗怎么出来，状态怎么变。

而这些动效，在真实代码写出来之前是不存在的。所以只能靠一段自动生成的走查视频，假装它在跑。

这个技能的工程量也不小：它得知道哪些屏幕是一组、它们之间的顺序是什么、镜头该在哪里推近、转场该多长。而这些判断，是从设计项目的结构里推出来的。

一个「设计转代码」的工具链，最后长出了一个「设计转视频」的分支。这件事本身挺有意思——它承认了在代码之前，还有一个更早的消费场景。

最后那句免责声明

仓库最后一段只有两句，而且两句都很硬：

这不是一个官方支持的 Google 产品。

这个项目不符合 Google 开源软件漏洞奖励计划的资格。

第一句划的是支持边界：Google Labs 出品，但不是产品，没有 SLA，没有客服。

第二句更少见。它说的是：如果你在这个仓库里发现一个安全漏洞，别指望拿到赏金。

一个项目愿意把「我们不付钱」写在正文最后，比它写十句「欢迎提交安全问题」要清楚。因为安全研究者的时间是有成本的，让他们在开始之前就知道规则，是一种尊重。

顺带说，Apache 2.0 的许可，加上这么一句，边界就又清了一层：代码你可以随便用，但别把这里当成 Google 的服务。

最后

回到那个双向的路。

从设计到代码，这个方向大家都在做，因为它是「AI 帮人干活」最直观的样子。

而从代码到设计，这个方向少有人做，因为它不酷——它是给迁移、给重构、给那些「我们已经有一万行 CSS 了，能不能先把它整理出来」的场景用的。

但后者可能更接近真实工作的样子。因为绝大多数团队不是从零开始画一个新界面，是继承一个已经长了五年的界面，然后试图让它变得更好一点。

而这套技能给出的办法，说到底很朴素：先把设计写成字，再让字去驱动代码。

一份 Markdown 夹在中间，两个方向都能走。它比设计稿好改，比截图好搜，比口头约定好版本管理。

至于它能不能真的把「设计」这件事说清楚——那是另一回事。有些东西写不进 Markdown，比如手感，比如那种「这里应该更安静一点」的判断。

但至少，那些能写进去的部分，现在有地方放了。
